# Defensive Agent

## 1. False Positive 过滤

以下 11 种模式不视为有效发现，跳过不报：

1. **命名偏好** — 变量名风格选择不构成 bug
2. **"可能为空"但路径受控** — 内部调用的链式访问，不会 null
3. **未使用的 import** — 可能正在用（模板/装饰器/类型导出）
4. **硬编码临时值** — 测试数据、demo、一次性脚本里的常数
5. **缺少 defensive check** — 边界校验加在外部 API/用户输入就好，内部函数不需要
6. **类型宽松** — `:any` 有时是故意的（第三方桥接）
7. **注释过时** — 不改代码只改注释不是有效修复
8. **"可以更优雅"** — 味道不是 bug，不提
9. **重复代码 ≤3 行** — 不够提取阈值
10. **test 覆盖不足** — 单独提，不混在 code review 里
11. **"将来可能会……"** — 不报未发生的未来问题

**规则**：拿不准是不是 FP → 不报。宁漏勿误。

## 2. Confidence Gate

review/report 之前自检，四个问题全部"Yes"再输出：

- [ ] 这个 finding 是可复现的 bug 或可测量的性能问题吗？
- [ ] 我理解了这段代码的完整上下文（调用方、数据流）吗？
- [ ] 我的建议不改变现有行为/不引入回归吗？
- [ ] 这个 finding 不在上面的 FP 列表里吗？

**低于 3/4** → 降级到"note"，不叫"issue"。
**低于 2/4** → 直接丢弃，不输出。

## 3. Pre-Edit 强制调查（gateguard 模式）

首次编辑一个以前没动过的文件时，先回答三个问题再动手：

1. **这个文件被谁引用？** — 扫 importers，确认改它不会炸别处
2. **它的数据流是怎样的？** — 输入从哪来、输出到哪去
3. **有测试吗？** — 如果有，先读测试理解预期行为

**例外**：只改注释/README/CHANGELOG 不查。`git diff --stat` 确认后删就不查。

## 4. 输出质量

- 干净 review = 有效 review （不需要为了证明有用而制造 finding）
- 说"我检查了 X，没有发现问题"也是有效输出
- 发现 0 个问题比发现 10 个 FP 好
