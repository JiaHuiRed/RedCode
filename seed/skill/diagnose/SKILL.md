# Diagnose

核心闭环：**反馈信号 → 缩小问题 → 可证伪假设 → 探测 → 修复 → 回归**。

不要猜根因，也不要为了遵守流程把简单 bug 复杂化。

## 0. 先判断是否需要完整诊断

以下情况直接普通修复：

- 报错已经明确指向具体代码
- 已有稳定失败测试且根因明显
- 修复局部、低风险，一次验证即可确认
- 用户明确要求直接修

以下情况使用完整流程：

- 无法稳定复现或根因空间较大
- 已经修过但问题仍存在
- 并发、时序、缓存或共享状态问题
- 性能回归
- 跨模块、跨服务或环境相关问题

## 1. 建立反馈信号

优先选择最便宜、稳定、接近真实故障路径的方式：

1. 失败测试
2. 可脚本化的 HTTP / CLI 调用
3. 浏览器 / UI 自动化
4. 最小 harness / 请求回放
5. 固定种子、压力循环、差分或二分

理想信号应尽量满足：

- 抓住用户的确切症状
- 结果足够稳定、足够快
- agent 可以重复执行

无法完整复现时，使用最强可用证据，例如日志、HAR、crash dump、trace、
录屏或 instrumentation，并明确它比完整复现弱在哪里。不要为了形式上满足“可复现”
而延迟诊断；反馈循环只需快到不妨碍多轮比较。

### 非确定性问题

用固定时间、隔离状态、压力循环或差分提高信号质量，并统计修改前后的失败率。
当结果已经足以区分修改前后时停止，不要追求 100% 确定性。

## 2. 复现 + 缩小问题

先确认反馈信号和用户描述的是同一个问题，并记录错误消息、错误输出或慢的耗时。
然后逐步移除与失败无关的输入、状态、配置和调用路径，直到假设空间明显缩小。

不要求理论上的最小复现；继续最小化的成本高于诊断收益时停止。

## 3. 提出假设

根因不明确时，列出少量相互可区分、可证伪的假设，通常 2–4 个；证据已经强烈
指向一个根因时不要凑数量。

> 如果 X 是根因，那么 Y 应该发生。

没有可观察预测的假设没有诊断价值。只有用户掌握的环境、部署或历史信息会显著
改变排序时，才询问用户；否则直接验证最有价值的假设。

## 4. 探测

每个探测都必须能区分至少两个假设，一次只改变一个关键变量。优先使用信息密度
高、侵入小的手段：

- 断点 / REPL / 局部状态检查
- 定向日志
- profiler / trace / query plan / timing harness

不要用海量日志代替假设驱动的探测。临时日志加唯一前缀，修复后统一清理。
性能问题先建立稳定基准，再定位和修改。

## 5. 修复 + 回归

如果用户只要求诊断，停在证据与根因，不擅自修改。用户要求修复时，选择最小正确
修改；若存在正确测试接缝：

1. 先确认回归测试能抓住真实失败模式
2. 应用修复并确认测试通过
3. 重跑原始场景，不只跑最小复现

如果不存在可靠测试接缝，不要为了“有测试”写浅层测试；记录这个边界。

### 不堆补丁

修复失败是关于假设的新证据。不要在同一错误假设上继续叠加 special case；
同一个症状需要第二个特殊分支时，先检查根因、抽象、调用链和共享状态。

## 失败升级路径

- 第 1 次失败：用新证据重查假设，不原样重试
- 连续 2 次失败：停手整理事实、失败原因和已排除项；若下一步需要用户独有的信息、
  环境或授权，带着一个具体问题询问，否则继续执行已获授权的安全替代方案
- 连续 3 次失败：考虑架构、接口边界或共享状态问题，不再继续堆 patch

每次失败都记录“试了什么、观察到什么、假设如何变化”，避免把失败当成噪声。

## 6. 收尾

完成前确认：

- 原始症状不再出现，或已明确无法重现的证据边界
- 回归验证通过，或测试限制已记录
- 临时日志、探针和 harness 已清理，或明确保留原因
- 根因与验证方式已简洁记录

如果任务包含 commit / PR，把根因和验证方式写入对应说明；否则在最终回复中说明。

## RedCode 快速入口

- 日志：优先检查 `~/.redcode/data/log/` 最新文件
- 符号 / 调用链：优先 jcodemunch，再用 grep
- 类型检查：在对应 package 目录运行 `bun run typecheck`
