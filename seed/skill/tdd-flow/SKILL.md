# tdd-flow

> 把大功能从"想法"安全送到"已验证落地"。核心是**测试先行**，把 RedCode 已有的 worktree / 子代理 / ce-code-review / diagnose 串成一条有门控的流程，并用假阳性过滤和置信度闸管住自己的判断。不发明新机制，只补纪律。

## TL;DR

| 项 | 说明 |
|----|------|
| 何时用 | 跨 3+ 步、触多文件、做坏代价大的功能；用户说"认真/严格/稳/小心" |
| 何时不用 | 一行修复、typo、纯探索、quick 改动 |
| 核心 | 测试先行：先写测试描述"做对"长什么样，再写实现 |
| 红线 | 永不 push；按影响面验证；未经用户明确要求不 commit |

## 流程

1 **澄清** 不确定就一次性问清（验收标准/边界/破坏性变更/能否复用现成的）
2 **计划** todowrite 拆成可独立验证的小任务，先给用户看一眼。质量门禁见下
3 **隔离** 大功能开 worktree（可选）；worktree 子代理别配 background
4 **实现** 测试先行，逐任务推进；**首次编辑不熟的文件先做三问**（见下）
5 **审查** 交给 ce-code-review，别自审交付；发现走假阳性过滤 + 置信度闸（见下）
6 **收尾** 按影响面验证通过；仓库级改动或用户明确要求时才跑全量 → 交回

小功能可跳 1/3/5，但**测试先行**和**收尾验证**是底线。

## 计划质量门禁

计划是给"没有上下文、品味存疑、不爱测试"的执行者看的——包括未来的自己。以下都是**计划失败**，当场改：

- **占位符**："TBD" / "加适当错误处理" / "写测试"（不附测试代码）——执行时全靠猜
- **模糊引用**："类似 Task N"——代码要重复写全，执行者可能倒序读
- **不可独立验证**：每个任务必须以自己能跑通的一条命令结尾
- **接口没写签名**：任务间共享的函数/类型，写明名字、参数、返回类型
- **引用不存在的东西**：任务里出现的函数/类型必须在前序任务定义过

todo 是执行台账：进度、修了几轮、决定都记在 todo 和项目记忆。上下文压缩后**只信 todo + git log，不信自己的记忆**。

## 首次编辑不熟文件的三问（pre-edit 调查）

第一次动一个以前没改过的文件，先回答再动手：

1. **谁引用它？** 扫 importers，确认改它不会炸别处
2. **数据流是什么？** 输入从哪来、输出到哪去
3. **有测试吗？** 有就先读测试理解预期行为

例外：只改注释/README/CHANGELOG 不查。

## 测试先行（核心）

默认顺序：**先写测试 → 跑一次看它失败 → 写实现让它过 → 顺手重构**。

- 写测试时想清楚"做对了"长什么样，比直接写实现更能暴露需求盲区
- **没亲眼看过它失败 = 这测试白写**。跑一次看红灯；没红过的测试删了重写
- 实现只写够让测试过的量，别顺手做下个任务
- 这是默认建议不是铁律：简单逻辑或测试成本明显大于收益时直接实现+补关键测试；**核心逻辑、边界多、易回归的地方坚持先行**

## 审查纪律：假阳性过滤 + 置信度闸

### 11 种不报的"发现"（FP 过滤）

1. 命名偏好（变量风格不是 bug） 2. "可能为空"但路径受控 3. 未使用的 import（可能在模板/类型里用） 4. 测试/demo 里的硬编码 5. 内部函数缺边界校验（校验加在外部入口就好） 6. `:any` 有时是故意的第三方桥接 7. 只改注释不算修复 8. "可以更优雅"是味道不是 bug 9. 重复 ≤3 行不到提取阈值 10. **泛化的**覆盖率建议（「这里测试不够」）单独提、不混 review——但**具体可复现的缺失回归断言**（明确行为风险 + 触发组合，如「折叠阈值在 clamp 后判定，没有 min>threshold 组合的测试」）是有效 finding，不得被本条过滤 11. "将来可能会……"不报未发生的问题

**拿不准是不是 FP → 不报。宁漏勿误。**（第 10 条的区分除外：具体断言缺口拿不准时**保留**并注明不确定，不适用宁漏勿误）

### 置信度闸（输出前四问）

- [ ] 是可复现的 bug 或可测量的性能问题吗？
- [ ] 我理解了完整上下文（调用方、数据流）吗？
- [ ] 建议不改变现有行为、不引入回归吗？
- [ ] 不在上面的 FP 列表里吗？

**=3/4** 降级为 note；**≤2/4** 直接丢弃（4/4 正常报，没有中间档）。

干净 review = 有效 review：「我检查了 X，没有发现问题」是好输出，发现 0 个问题比 10 个 FP 好。

## 收尾清单

1. 按影响面验证：受影响 package 的 typecheck + 对应测试全绿；仓库级改动才跑全量（TUI→packages/opencode，GUI→packages/desktop）
2. 改了接口 → 用符号检索确认调用方都更新了
3. 仅在用户明确要求后 commit：遵循项目 git log 风格
4. worktree 合回（如开了）
5. 报告做了什么和验证结果；commit、push 需用户明确要求

## Anti-patterns

- 假 TDD：先写实现再补测试，或测试从没真红过
- 占位符计划：执行时全靠猜
- 自审交付：自己说"看着没问题"就交，不换 ce-code-review 的眼睛
- FP 洪水：为证明审查有用而制造 finding
- 滥用：拿这套流程做一行修复，为走流程烧 token

## 关系

- `goal-automation` 跑长流程前先 /goal 钉目标防跑偏
- `ce-code-review` 第 5 步的审查执行者（FP 过滤与置信度闸同样适用于它的输出；编排下它**不 commit**——它的权限优先级是 用户授权 > 本工作流约束 > 它自己的默认行为，收尾统一走上面清单第 3 条）
- `diagnose` 发现 bug 时的调试纪律
- `simplify` 审查发现过度工程时的精简纪律
