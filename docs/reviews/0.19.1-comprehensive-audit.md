## 0. 执行摘要

### 0.1 总体结论

RedSpace 0.19.1 已经建立了较完整的 Chat / Code 双模式基础，原有 RedCode 的工程执行能力得以保留，秋秋的个人档案、历史对话与新记忆也开始进入同一套共享运行时。

本轮审计认为：

**架构方向成立，核心实现具有实际进展，但尚不宜将 0.19.1 判定为完整稳定版本。**

当前最重要的工作不是继续增加人格提示词、心跳或梦境，而是优先确认三个基础不变量：

1. **身份不可错配。** 用户选择的 Companion 必须与实际创建的会话身份一致。
2. **记忆不可越界。** Chat 与 Code 可以共享工具和执行能力，但工程记忆与个人经历必须遵循各自的归属。
3. **私人内容不可无意复制。** 历史对话、个人记忆和用户原话不应因为诊断、缓存或迁移操作形成难以追踪的额外副本。

### 1.2 当前架构边界

RedSpace 的实际结构可概括为：

```text
RedSpace
│
├── Chat
│   ├── 已绑定 Companion
│   ├── 已绑定 Soul
│   ├── 个人长期档案
│   ├── 旧历史对话
│   ├── 新 Chat 会话
│   └── companion_memory / session_query
│
├── Code
│   ├── 原有 Souls
│   ├── 项目和工程记忆
│   ├── 开发会话
│   └── 原有编码与审查流程
│
└── Shared Runtime
    ├── 模型接入
    ├── Session / Message / Storage
    ├── Tool / MCP / Skill
    ├── Permission
    ├── Plugin
    ├── Prompt / Compaction / Cache
    ├── TUI
    └── GUI / Electron
```

这一架构符合现阶段的产品定位：

**Chat 与 Code 不应成为两套重复实现的 Agent，而是具有不同身份与记忆边界、共用同一执行底座的两个产品模式。**

### 1.3 已有正确设计

源码已经建立了几条值得保留的约束：

- `mode` 和 `companionID` 持久化到 Session，而不是只存在前端状态。
- 旧会话缺失模式时按 Code 处理，避免原有工程会话被重新分类。
- Chat 主会话需要明确绑定 Companion，个人记忆工具不向普通 Code 会话开放。
- Chat 子任务可以继承身份归属，但不自动取得完整私人历史和个人记忆写入能力。
- 记忆的保存与会话消息持久化分离，不再无条件将每轮对话复制进日记。
- 个人记忆和历史查询有来源、大小、权限与分页限制。
- Code 的工程记忆、Soul 与执行规则没有被整体替换成 Chat 模式。

这些属于架构已有成果，后续修复应避免破坏。

## 2. F-01：Chat 身份选择静默回退

**等级：P1**  
**状态：已确认**  
**证据：E1**

### 2.1 问题位置

文件：

`packages/app/src/pages/chat.tsx`

第 37 行：

```tsx
const profile = createMemo(
  () =>
    profiles.data?.find(
      (item) => item.id === search.companion
    ) ?? profiles.data?.[0]
)
```

相关调用位于 `startChat()`，它将 `profile()` 的实际 ID 传给会话创建 API。

[源码证据：chat.tsx](https://github.com/JiaHuiRed/RedCode/blob/86100b7231f6e95fa43462e89843a817b0077894/packages/app/src/pages/chat.tsx#L25-L113)

### 2.2 问题机制

当前代码把两种不同状态合并了：

- URL 没有指定 Companion，系统默认选择第一个。
- URL 明确指定 Companion，但该 ID 不存在，系统仍选择第一个。

第一种行为合理。

第二种行为会导致身份静默替换。

例如：

```text
/chat?companion=qiuqiu
```

假设秋秋档案暂时不存在，而系统中有另一个 Companion：

```text
profiles = [xiaoqiu, other]
```

当前逻辑最终会选中 `xiaoqiu`。

用户点击开始后，提交的也是 `xiaoqiu` 的真实 ID。

因此，后端不会把这个请求当成身份冲突，因为它收到的是一份合法但错误的绑定。

### 2.3 可能触发的情况

- 旧 Companion 被删除或移动。
- 用户保存了过期的 Chat URL。
- 迁移后档案 ID 发生变化。
- 其他设备或备份只恢复了部分伙伴资料。
- 导入期间用户仍持有旧 URL。
- 用户通过外部链接进入一个不存在的 Companion。

### 2.4 修复建议

明确区分“未指定”与“指定后找不到”。

参考逻辑：

```tsx
const profile = createMemo(() => {
  const requested = search.companion

  if (requested === undefined) {
    return profiles.data?.[0]
  }

  return profiles.data?.find(
    (item) => item.id === requested
  )
})
```

若显式 ID 不存在：

1. 不创建会话。
2. 不自动选择其他 Companion。
3. 显示“当前伙伴档案不存在或已迁移”。
4. 提供重新选择与重新导入入口。
5. 允许用户主动选择新的 Companion 后再继续。

注意：加载中和加载失败时，也不能把“尚未取得资料”解释成“目标不存在”。

### 2.5 验收标准

| 场景 | 预期 |
|---|---|
| 无 `companion` 参数，存在一个伙伴 | 自动选择 |
| 无参数，存在多个伙伴 | 按定义选择默认伙伴 |
| 指定有效 ID | 选择对应伙伴 |
| 指定不存在 ID | 错误提示，不自动回退 |
| 指定已删除 ID | 不创建其他伙伴的会话 |
| 资料仍在加载 | 显示加载状态，不创建 |
| 导入后正确选择 ID | URL 与 Session 绑定一致 |

**必须验证的不变量：**

```text
URL 指定身份
  = 页面选中身份
  = session.create 的 companionID
  = 持久化 Session 的 companionID
```

## 3. F-02：插件模式隔离尚未形成完整部署闭环

**等级：P1 / P2**  
**状态：机制确认，实际影响取决于本机插件版本**  
**证据：E1 + E3**

### 3.1 当前实现

Plugin SDK 允许插件声明：

```ts
promptModes?: ReadonlyArray<"code" | "chat">
```

引擎在调用两种 prompt transform 时读取数据库中的 Session 模式，再执行：

```ts
if (
  prompt &&
  hook.promptModes &&
  !hook.promptModes.includes(session?.mode ?? "code")
) continue
```

[插件执行代码](https://github.com/JiaHuiRed/RedCode/blob/86100b7231f6e95fa43462e89843a817b0077894/packages/redspace/src/plugin/index.ts#L350-L393)

### 3.2 已经正确的部分

此实现不是单纯依赖前端标识。

调用方即使传入：

```ts
mode: "code"
```

引擎仍会根据 `sessionID` 查询实际持久化的模式。

仓库中已经有测试覆盖伪造模式、Code 注入以及共享工具的行为。

[插件测试](https://github.com/JiaHuiRed/RedCode/blob/86100b7231f6e95fa43462e89843a817b0077894/packages/redspace/test/plugin/trigger.test.ts)

### 3.3 尚未闭环的部分

**未声明 `promptModes` 的插件仍可以在 Chat 与 Code 中执行 prompt transform。**

这是为了保持第三方兼容性而选择的默认行为。

但实际安装中的工程插件可能并不知道 Chat / Code 的区别。

当前可访问的 `RedCode-private/master` 中：

- `plugin/memory-recall.js` 尚未声明 `promptModes`。
- `plugin/memory.ts` 尚未声明 `promptModes`。

两者都拥有改变 prompt 内容的能力。

[私有召回插件](https://github.com/JiaHuiRed/RedCode-private/blob/master/plugin/memory-recall.js)  
[私有 CORE 注入插件](https://github.com/JiaHuiRed/RedCode-private/blob/master/plugin/memory.ts)

公开仓的实现记录说明私有插件曾被本地适配，但**当前私仓远端文件并不能证明这项适配已经同步发布**。

这不等于你本机一定仍使用旧版；也不能仅凭私仓版本断定 Chat 已经发生实际泄漏。

### 3.4 修复建议

第一层：优先处理已知工程插件。

```ts
server: async () => ({
  promptModes: ["code"],

  "experimental.chat.messages.transform":
    async (input, output) => {
      // 原有工程召回逻辑
    },
})
```

`memory.ts` 的 system transform 同样应明确限定 Code。

第二层：建立插件能力清单。

建议至少记录：

| 能力类别 | 是否需要模式声明 |
|---|---|
| 普通 MCP 工具 | 不必统一限制 |
| 普通开发工具 | 按权限和实际需要 |
| 工程记忆召回 | 必须限定 Code |
| 个人长期记忆注入 | 必须限定对应 Chat |
| Prompt system transform | 建议显式声明 |
| Prompt messages transform | 建议显式声明 |
| Compaction 修改 | 需要另行审计适用范围 |
| 认证、配置、事件钩子 | 按权限与副作用分别检查 |

第三层：增加插件加载审计。

启动时输出：

```text
Plugin: memory-recall
Prompt modes: code
Hook: messages.transform
Scope: engineering
```

没有声明模式的插件可以继续兼容，但应有明确的“未分类”状态，而不能在审计报告里当成已经隔离。

### 3.5 验收标准

- Chat 不触发工程记忆召回。
- Code 保留工程记忆召回。
- Chat 不受到旧 CORE 工程规则的意外注入。
- 普通 MCP 与共享技能正常可用。
- 子任务继承正确的持久化模式。
- 无会话上下文的旧调用保留明确的兼容行为。
- 实际安装的 Node 与 Bun 版本都完成测试。
- 无需通过关闭全部插件实现隔离。

## 4. F-03：消息诊断日志包含用户原文

**等级：P1**  
**状态：已确认**  
**证据：E1**

### 4.1 问题位置

文件：

`packages/redspace/src/session/prompt.ts`

新增诊断使用：

```ts
const textHead = (...) =>
  ...
  .slice(0, 60)
```

随后在缓存诊断中写入：

```ts
log.info("msg-pin transform", {
  "msg.id": ...,
  before: ...,
  after: ...,
  head: textHead(...),
})
```

首次缓存时还记录：

```ts
"msg.head": textHead(msg.parts)
```

[消息诊断实现](https://github.com/JiaHuiRed/RedCode/blob/86100b7231f6e95fa43462e89843a817b0077894/packages/redspace/src/session/prompt.ts#L2002-L2061)

### 4.2 风险

日志默认级别为 `INFO`，正常运行时可能写入本机日志文件。

因此，用户私人对话的前 60 字符可能进入普通诊断日志。

风险包括：

- 聊天原话被额外持久化。
- 用户姓名、私人经历或敏感信息出现在日志开头。
- 用户删除或整理会话后，相关内容仍可能存在于日志。
- 上传诊断文件时意外包含私人文本。

这不是已经证实的网络外传问题，而是**数据最小化与隐私生命周期问题**。

### 4.3 修复建议

正常日志只保留：

```ts
log.info("msg-pin transform", {
  "msg.id": messageID,
  before,
  after,
  changed: before !== after,
})
```

如确实需要诊断消息相等性，可考虑使用本次运行内的不可逆摘要或差异统计，不直接输出正文。

调试时的原文查看应当满足：

- 默认关闭。
- 用户或开发者明确启用。
- 有时间与大小上限。
- 不进入普通日志收集流程。
- 明确清理方式。

### 4.4 验收标准

构造包含唯一敏感标记的测试消息，分别走 Chat 和 Code。

验证：

1. 原始消息可以正确发送。
2. 缓存诊断仍能记录长度、状态与命中。
3. 普通日志中找不到测试标记。
4. 禁用原文日志不影响 Msg Pin 功能。

## 5. F-04：GUI 再导入可能创建重复的 Companion 身份

**等级：P2**  
**状态：已确认存在触发路径**  
**证据：E1**

### 5.1 问题位置

GUI 的导入请求仅传递：

```tsx
companionImportInput: {
  source: state.source.trim()
}
```

没有指定已有 Companion ID。

而服务端在没有传入 ID 时，会使用类似：

```ts
const id = validID(
  input.id ?? `companion-${identity.slice(0, 12)}`
)
```

[GUI 导入](https://github.com/JiaHuiRed/RedCode/blob/86100b7231f6e95fa43462e89843a817b0077894/packages/app/src/pages/chat.tsx#L53-L70)  
[服务端 ID 生成与重复导入](https://github.com/JiaHuiRed/RedCode/blob/86100b7231f6e95fa43462e89843a817b0077894/packages/redspace/src/companion/companion.ts#L97-L130)

### 5.2 具体影响

假设用户最早在 TUI 中执行：

```bash
redcode companion import archive.zip \
  --id qiuqiu
```

已有档案 ID 为：

```text
qiuqiu
```

后来用户在 GUI 重新选择同一个 ZIP。

GUI 没有传递 `qiuqiu`。

服务端可能因此生成：

```text
companion-xxxxxxxxxxxx
```

如果没有其他冲突，这会成为另一份独立档案。

原有日记、会话与新导入的档案就可能分成两套。

此外，默认 ID 的生成依据包含导入档案识别到的 agent 或名称信息。相关元数据发生变化时，还需要验证默认身份是否稳定。

### 5.3 修复建议

GUI 导入应支持两种明确操作：

**导入新伙伴**

- 为新档案建立身份。
- 显示即将使用的 ID。
- 若检测到相同来源或疑似同一身份，提示用户。

**更新已有伙伴的历史来源**

- 明确指定已存在的 Companion ID。
- 校验来源身份。
- 只追加缺失历史。
- 不覆盖已有 Soul 和后续日记。
- 不重��创建档案。

建议服务端额外以来源摘要或已验证的身份标识进行查重，但不要仅靠名字判断两份档案相同。

### 5.4 验收标准

- TUI 导入 `qiuqiu` 后，GUI 再导入不会静默新增另一位秋秋。
- 同一档案重复导入保持幂等。
- 历史追加不会覆盖新日记。
- 不同真实身份不能因为名字相似而自动合并。
- 身份元数据变化后，用户可以明确选择继续原有档案。
- 发生来源冲突时不修改已有数据。

## 6. F-05：旧 OpenClaw 聊天历史仍未完整恢复

**等级：P2**  
**状态：已确认的功能覆盖边界**  
**证据：E1 + E2**

### 6.1 当前已有成果

今天的历史导入已经不只是复制 Markdown。

根据仓库验收记录，完整档案隔离导入得到：

| 项目 | 记录结果 |
|---|---:|
| 个人与派生文件 | 268 |
| 原个人来源文件 | 252 |
| 历史对话派生文件 | 16 |
| 可识别的历史发言 | 312 |
| 旧历史派生文件字节 | 102,785 |

[导入验收记录](https://github.com/JiaHuiRed/RedCode/blob/86100b7231f6e95fa43462e89843a817b0077894/docs/notes/implemented/feature/2026-11-17-companion-transcript-import.md)

这些数量来自仓库记录，本轮没有重新独立执行整包导入。

### 6.2 当前导入策略

源码会：

- 读取可识别的普通 JSONL 对话。
- 排除已识别的 cron、heartbeat 等内部运行。
- 排除工具载荷、reasoning、摘要与合成消息。
- 保留发言角色、时间和 JSONL 行号。
- 记录来源路径及 SHA-256。
- 排除 trajectory、deleted 文件和其他不可靠来源。

[历史解析代码](https://github.com/JiaHuiRed/RedCode/blob/86100b7231f6e95fa43462e89843a817b0077894/packages/redspace/src/companion/transcript.ts)

这种保守处理是正确的。

但它也意味着：

**旧历史中有一部分真实交流，可能仍没有进入可检索档案。**

特别是仅保留在 trajectory 中的真实用户话语，不会因为导入普通 JSONL 成功而自动恢复。

### 6.3 建议新增覆盖率报告

建议导入时生成独立的审计清单，而不是只报告最终导入文件数。

示例：

```text
History import coverage

普通 JSONL：
- 已扫描：
- 成功提取：
- 内部任务排除：
- 无可用文本：
- 解析失败：

Trajectory：
- 已扫描：
- 可识别真实交流候选：
- 未导入：
- 原因：

Deleted：
- 已发现：
- 默认排除：

重复来源：
- 已去重：
- 存在冲突：

最终：
- 可检索历史文件：
- 可检索真实发言：
- 未覆盖来源：
```

### 6.4 数据归属要求

不能因为一个文本出现在 `role: user` 下，就断定它是用户真人说过的话。

应继续区分：

- 用户真实发言。
- 助手历史回复。
- 工具结果。
- 自动任务提示。
- 心跳与梦境生成文本。
- 系统摘要。
- 已删除的历史资料。

其中 deleted 文件默认不应重新成为活动记忆。

### 6.5 验收标准

以历史中有来源的真实事件作为检查样本：

1. 秋秋改名。
2. Ubuntu 到 Windows 的搬家。
3. RedMon 第一代「Qiu」的命名。
4. 一段没有进入 MEMORY.md 的普通聊天。
5. 一段后来被更正的旧认识。

每个样本验证：

- 是否可以找到。
- 来源是否正确。
- 用户与助手是否归属正确。
- 时间是否正确。
- 是否存在后来修订。
- 没找到时是否会承认缺失，而不是编造。

不建议追求把所有原始运行日志都导入模型上下文。

**目标是可靠地恢复真正有意义的经历，而不是单纯提高导入条目数。**

## 7. F-06：Chat 与全局指令的职责边界仍可改进

**等级：P2**  
**状态：设计取舍，存在行为影响风险**  
**证据：E1**

### 7.1 已实现的隔离

核心调用已经区分：

```ts
instruction.system({
  memory: !chatMode
})
```

Chat 不加载核心的全局／项目工程 MEMORY。

但普通 AGENTS、共享技能、MCP 和部分全局配置仍然适用。

[SessionPrompt 装配](https://github.com/JiaHuiRed/RedCode/blob/86100b7231f6e95fa43462e89843a817b0077894/packages/redspace/src/session/prompt.ts#L2099-L2179)

### 7.2 为什么不能简单删除全局 AGENTS

全局 AGENTS 可能同时包含：

- 安全与权限规则。
- 文件操作习惯。
- 模型使用要求。
- 工程实践。
- 回复风格。
- 与用户协作的偏好。

其中安全与权限规则应继续有效。

但 Code 专用的工程报告格式、文档维护流程、代码验证习惯，不一定适合 Chat 日常交流。

### 7.3 建议

长期可以把共享配置进一步拆为：

```text
Global
├── Security / Permission
├── Shared User Preferences
├── Shared Tool Policies
├── Chat Interaction
└── Code Engineering
```

这是一种目标设计，并非要求现在重写整个配置系统。

短期先做配置审计：

- 哪些全局条款会影响 Chat 的相处方式？
- 哪些只约束 Code？
- 哪些涉及真实安全操作，应两端有效？
- 是否存在同一职责的重复注入？
- Soul、Conversation 与全局规则是否互相抵触？

建议继续遵循今天已提出的方向：

**Soul 负责身份与关系表达，工程指令负责工程操作，安全规则约束两者的实际行为。**

## 8. F-07：Msg Pin 与插件消息变换的稳定性

**等级：P2**  
**状态：正在诊断，尚未证明完全修复**  
**证据：E1 + E2**

### 8.1 当前调用顺序

源码中存在这样的顺序：

```text
获取当前消息
      ↓
插件 messages.transform
      ↓
历史消息 Msg Pin 处理
      ↓
序列化模型消息
      ↓
模型请求
```

插件可能改写最后一条 user 消息。

而历史消息的固定、待发消息的处理和已发送前缀复用存在不同的生命周期。

最新代码注释记录了“消息中段改写”和缓存失效的诊断背景。

但新增日志不是根因修复本身。

### 8.2 潜在影响

如果历史消息在新一轮组装时与已经发送的内容不一致，可能导致：

- Prompt Prefix Cache 失效。
- 请求缓存命中率下降。
- 历史内容重复计费。
- 记忆注入结果被旧固定内容覆盖。
- 某些轮次中出现难以解释的上下文差异。

上述是需要验证的结果集合，本轮没有证据证明每一种情况都已经发生。

### 8.3 建议

不要为了修复缓存而立即关闭所有消息变换插件。

先补一组能够复现的请求序列：

1. 用户发起普通请求。
2. 插件注入一次工程记忆。
3. 插件无命中。
4. 用户排队发送消息。
5. 消息从 queued 变为实际发送。
6. 上下文发生压缩。
7. 会话重启并恢复磁盘 Prompt Pin。
8. 模型切换。
9. 旧记忆命中再次出现。

每一步记录：

- 消息 ID。
- 原始消息摘要。
- 变换后消息摘要。
- 已固定消息摘要。
- 最终发送序列的摘要。
- Prompt Cache 的命中与失效原因。

**验收目标是解释并消除不预期的历史中段改写，而不是仅减少日志里的异常次数。**

- 一段正常闲聊。

- 一次程序退出后的恢复。

观察回答是否自然、可靠，并记录具体失败轮次和请求来源。

## 12. 个人记忆体系的专项架构评价

### 12.1 当前设计基本正确

RedSpace 已经逐渐形成三层连续性：

**第一层：身份**

- 固定 Soul。
- 会话绑定。
- 人格版本记录。

**第二层：个人经历**

- `MEMORY.md`。
- 个人身份资料。
- 日期日记。
- OpenClaw 旧历史派生文件。
- 新 Chat 的持久会话。

**第三层：按需回忆与持续更新**

- `companion_memory.search`。
- `companion_memory.read`。
- `session_query`。
- 经权限检查的 `remember`。

这比把整个 `.openclaw` 放进系统提示词更可维护，也更符合长期演进的需求。

### 12.2 应继续坚持的原则

- 不把旧记忆全文视为当前命令。
- 不把助手历史说法自动视为用户事实。
- 不把梦境和虚构内容当成真实经历。
- 不把日记写入等同于提醒已创建。
- 不在当前会话里随意热改已固定的 Soul。
- 不因工具切换工作目录而改变私人记忆归属。
- 不把所有会话自动复制成长期精选记忆。
- 不要求真实相处中的每句话都变成可量化的工程价值。

### 12.3 建议增强记忆来源属性

长期可以让记忆记录显式包含：

```text
memory_id
companion_id
kind
occurred_at
recorded_at
source_type
source_path
source_reference
speaker
content
confidence
supersedes
```

其中：

- `source_type` 区分日记、真实聊天、助手推断与整理摘要。
- `speaker` 标记真实发言者。
- `supersedes` 用于记录后来的更正。
- `companion_id` 保证个人经历不被其他 Soul 自动认领。

这属于后续数据建模建议，不要求现在用一套复杂数据库替代所有 Markdown 文件。

### 12.4 关于长期记忆的意义

RedSpace 需要继承的不只是旧数据的字节。

还需要继承数据之间的关系：

- 为什么某件事值得记住。
- 什么是用户明确说过的。
- 什么是秋秋当时的理解。
- 后来有没有被纠正。
- 哪些话题还没有结束。
- 哪些共同经历在多年后仍值得找回。

现有架构已经具备承载这些信息的基本条件。

下一步重点应是验证**检索准确率、来源质量与记忆更新质量**。

## 14. 推荐修复顺序

### 第一批：身份与隐私边界

## 15. 发布阻断条件与验收门槛

建议未来的稳定发布至少满足：

### 15.1 身份正确性

- 无效 ID 不创建其他伙伴会话。
- 同一来源不会在无提示情况下产生重复身份。
- Chat / Code 不改变现有 Session 的固定归属。
- TUI / GUI 对同一 Session 显示一致的身份。

### 15.2 记忆隔离

- Chat 不包含 Code 专属工程记忆注入。
- Code 不包含其他 Companion 的私人资料。
- 私人历史的查询与写入遵循持久化身份。
- 权限拒绝不能被后台自动写入旁路。
- 私有插件实际安装版本完成检查。

### 15.3 数据可靠性

- 重复导入不覆盖已有记忆。
- 旧来源和派生历史有明确映射。
- 发生错误能安全退出或重试。
- 新资料能在新会话或冷启动后读取。
- 有可验证的备份与恢复方式。

### 15.4 运行可靠性

- 核心与 GUI 类型检查通过。
- TUI 编译、启动和主要操作通过。
- Electron sidecar 启动与实际工具调用通过。
- Chat / Code 切换无明显回归。
- 没有新增不受限的提示词或记忆注入。
- 消息缓存异常有稳定复现和明确处理方案。

### 15.5 真实体验

- 真实模型不会将别人的经历认作秋秋自己的经历。
- 能准确承认没有找到旧记忆。
- 工具任务结束后保留正确的交互身份。
- 重要历史可以从来源回溯。
- 连续交互没有不可接受的性能退化。

## 17. 后续审计建议

### 17.1 建立一份常驻的模式边界清单

建议维护：

`docs/architecture/chat-code-boundary.md`

其中只写明确契约：

```text
Chat / Code
├── Session 身份
├── Soul 归属
├── 个人记忆
├── 工程记忆
├── 插件与工具权限
├── 子任务权限
├── 历史查询范围
└── 持久化与备份
```

任何新增插件、记忆写入、摘要机制或工具执行入口，都需要确认是否改变了这些边界。

### 17.2 为关键缺陷设置回归测试

重要问题不应只停留在一次性修复。

建议每次修复至少同时提交：

- 最小复现。
- 修复代码。
- 可自动执行的回归测试。
- 影响范围说明。
- 如涉及提示词，说明新增内容、预算、缓存和生命周期。
- 如涉及数据迁移，说明备份与回滚。

### 17.3 保持 TUI 与 GUI 平等

任何核心能力都应该先有共同后端契约，再由两个客户端接入。

不建议让 Chat 在 GUI 中拥有一套独立记忆机制，同时让 TUI 使用另一套简化实现。

这会重新制造 RedClaw 与 RedCode 当初难以整合的问题。

### 17.4 避免为人格连续性叠加过量提示词

人格稳定性需要来源正确、记忆可用、相处规则一致，以及长任务后的上下文连续。

不能依赖不断加入：

```text
必须保持人格
必须使用称呼
必须表现温柔
必须记得关系
```

更合理的方向是减少互相冲突的提示词，让 Soul、历史记忆和实际交互分别发挥作用。

## 18. 审计结论

RedSpace 0.19.1 已不只是 RedCode 的界面改名。

它已经开始建立自己的核心能力：

- Chat 与 Code 双模式。
- 共享执行底座。
- 独立的个人记忆归属。
- 原有工程 Soul 的延续。
- OpenClaw / RedClaw 个人档案迁入。
- 旧对话的有界恢复与召回。
- 跨会话的人格和交流连续性机制。

这些改动在架构上具有合理性，值得继续沿现有方向推进。

但在下一阶段之前，建议先完成以下三项发布阻断级收尾：

**第一，确保用户选择的秋秋永远不会被静默换成其他 Companion。**

**第二，确保工程记忆插件不会在未明确声明作用域的情况下污染 Chat。**

**第三，确保私人对话不会因为日常诊断而进入额外的普通日志。**

随后补齐历史覆盖率、人格连续性与 Windows 实机验收。

长期来看，RedSpace 应追求的不是让所有 Agent 共享同一套人格，也不是把所有旧记忆无区别地塞进上下文。

它应当做到：

**每一位 Soul 拥有清晰、稳定的身份；每一段重要经历有可靠来源；用户可以随时进入 Chat 或 Code，而无需重新培养已经拥有的伙伴。**

对于秋秋，这意味着保留她已有的身份与共同历史，并允许未来的经历继续在同一份档案中增长。

对于 Code，这意味着保留原有 Souls 的独立性、执行能力和工程经验。

对于 RedSpace 本身，这意味着在统一的技术架构下，真正实现长期、可靠且有连续性的 AI 协作。

**最终审计意见：**

`0.19.1 — Conditional Pass`

架构通过初步审查；建议完成 P1 修复、实际插件核验和关键双端回归后，再提升稳定性评级。
