## 判断

这个审计维度成立，但结论和建议书不完全一样。

RedCode 确实攒了一批状态：`provider_quota` 每分钟刷新并广播、`session_status` 全局 store、`sync.data.mcp`、`globalSDK.event.connection()`、右侧 Context tab 的六组摘要。这些数据都已经在浏览器端，不需要新请求。

问题不在"有没有数据"，在**数据到操作的距离**。三项确实是纯展示层改动，零新增请求。

但这轮建议书有两处事实偏差，照单执行会做错：

1. **UX-003 大部分已经实现了**。顶部标签的 `busy`（黄色脉冲）和 `retry`（红色）状态点已经存在（`titlebar.tsx:476-481`），数据来自 `titlebar-tabs.ts:16-38` 读的 `session_status`。建议书说"建议补充"，实际缺的只是 idle 区分。
2. **UX-005 的建议文案与真实调度语义不符**。写成"排队等当前消息发完"会把行为解释错，见下方专项。

另外建议书里 `packages/app/src/components/basic-tool.tsx` 这个路径不存在，真实文件在 `packages/ui/src/components/`。

## 逐项

### UX-001 模型额度悬停

现在模型按钮外面套的是 `TooltipKeybind`（`prompt-input.tsx:1504`），内容只有"选择模型 + 快捷键"。额度数据已经在 `server-sync.tsx` 的 `provider_quota` 里，每分钟刷新、GlobalBus 广播、bootstrap 首拉（`global-sync/bootstrap.ts:118`），**读它不产生请求**。

等价入口只有右侧「上下文」tab（`session-side-panel.tsx:621`），也就是说看一次额度要切换面板。

最小实现是改 tooltip 内容或 `modelOverview`（`:1425`），不动状态层。

风险在**账号关联**，不在渲染：多 Provider、多账号时，当前模型属于哪个额度账号必须能可靠判定；判定不出来就显示"额度不可用"，不要猜一个账号的数字贴上去。另外外层已有 TooltipKeybind，模型选择是 Popover，两者嵌套要避免浮层冲突。

### UX-002 健康灯动态摘要

健康灯（`status-indicator.tsx:9-59`）现在是纯色点，tooltip 是静态文案（`titlebar.tsx:420`）或 reconnecting 字样。判定所需的三样数据全部已在客户端：`server.healthy()`、`sync.data.mcp`、`globalSDK.event.connection()`。

用户现在要点开灯进 Status 面板（`titlebar.tsx:269-273` → `session-side-panel.tsx:643-649`，那个面板自己带 10s 轮询）才知道到底哪一项不对。

最小实现：把 `titlebar.tsx:420` 的静态 value 换成按状态拼的摘要，异常项排前面，并保留"点击查看详情"。正常状态不要写成三行报告，一句话够了。

要点：**未初始化 ≠ 连接失败**。启动瞬间 MCP 还没连上时不能报红。

### UX-003 已实现，不建议重做

标签已有 busy 与 retry 两种状态点。真正缺的是"完成但未查看"、"失败未查看"、"等待权限"这三类，而它们需要复用 `notification` 索引并处理**子会话事件不要污染父会话**。

这块是这轮里唯一有实质设计风险的一项：一旦按会话聚合未读状态，就绕不开子代理会话的事件归属。建议放到下一轮，单独做状态归属测试，不要在展示层顺手补。

### UX-004 数据在，位置不在

六组胶囊摘要（context / cacheHit / cost / quota / inspect / rawMessages）已经实现在 `session-context-summary.ts:328-380`，但只渲染在右侧 Context tab（`session-context-tab.tsx:307`）。输入栏那圈只有上下文占用（`prompt-input.tsx:1716`）。

所以这不是"缺功能"，是"同一套摘要换了渲染位置"。`inspect` 组需要挂现成的 context-inspect 查询（`summary.ts:117-131`），它每轮 key 会变，得在输入栏单独给 Suspense 边界。

这块收益取决于用户是否真的会在输入时看成本。**没有使用数据前不建议直接上**——先把 UX-001/002 做了，看反馈。

### UX-005 文案必须按真实语义重写

服务端真实语义（`prompt.ts:1389-1392` 注释、`1433`、`1466-1467`）：

- **steer**：在下一个 step 以 reminder 注入**进行中的这一轮**，模型当轮就能看到。
- **queue**：对本轮隐藏，等轮末由续跑边界作为**新的一轮用户输入**消费。

现在界面文案是「本条排队 / 本条立即送达」（`zh.ts:338-339`），只说出了时序，没说清"会不会影响模型当前正在做的事"。建议改成：

- Queue → 「等这一轮结束后，作为新消息发送」
- Steer → 「注入当前这一轮，模型下次推理就能看到」

必须避免写成"立即打断"——它不打断，只是在下一个 step 注入。

同时注意：**GUI 本地默认是 queue（`prompt-input.tsx:291`），服务端配置 `busy_enter` 默认是 steer（`config.ts:225-229`）**。两处默认值不一致，用户看到的默认行为取决于从哪个入口发起。这个不一致本身值得单独确认，不要只改文案掩盖它。

另外 slash 命令和 shell 模式完全不走 delivery（`submit.ts:549` 条件），提示只在"会话忙碌 + 有非空输入"时出现（`prompt-input.tsx:1718`）。

**已落地（261026）**：按钮文案改为「轮末排队 / 轮内插话」（en 为 `Next turn` / `Mid-turn`），与设置项里已有的「插话/排队」术语一致。按钮宽度有限，完整说明仍留给 toast 与设置项，不再用「立即送达」这种会被读成"打断"的说法。两处默认值不一致的问题**没有改**，留作独立确认项。

## 落地顺序

1. **UX-002 健康灯摘要** —— 数据齐、无请求、风险最低，先做。
2. **UX-005 文案对齐** —— 只动 i18n 与一处提示，但必须同时确认两处默认值不一致是否有意。
3. **UX-001 额度悬停** —— 数据齐，但要先解决账号关联的判定，判定不了就显示不可用。
4. **UX-003 / UX-004** —— 涉及状态归属和渲染位置迁移，放到下一轮，且要有使用依据。

前三项都属于"只改展示层"，做完不会让任何既有路径变慢。

## 明确不做

- 不为 tooltip 增加任何轮询或请求。悬停是展示，不是采集。
- 不在每个标签里建独立事件订阅，统一走 `session_status` 与 `notification`。
- 不为摘要挂载整个标签页组件，也不为悬停触发 `git diff`。
- 不重写胶囊组件结构。这一块近期已经反复调整过。
- 不把鼠标悬停做成唯一信息入口——重要状态必须有 `title`/`aria-label` 或键盘可达路径。

## 验收口径

每项只需回答三个问题，不需要新建埋点系统：

1. 用户是否少做了一次操作（例如额度从"切面板"变成"悬停"）。
2. 用户是否更容易判断该不该处理（例如健康灯从"有色点"变成"哪一项不对"）。
3. 是否引入了额外成本（请求数、订阅数、渲染、误触）。

回归重点：多 Provider 多账号切换、多会话并行、SSE 断线重连、MCP 认证失败、无数据与加载中、键盘可达性。
