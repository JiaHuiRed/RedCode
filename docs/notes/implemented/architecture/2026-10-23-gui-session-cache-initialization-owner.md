# GUI 会话缓存与首次初始化收归明确的所有者

状态: implemented

## 问题

GUI 预取、前台同步和实际消息 Store 的生命周期不同：

- `createPrefetch` 的私有 LRU 在目录离开可见集时被删除，消息和 parts 却仍保存在 child Store。直接调用真实预取实现的对照中，连续预取受 10 会话预算约束，离开再返回目录后却保留了 20 份消息和 parts。
- `directory-sync` 另有前台 LRU，其上下文由 `createRefCountMap` 复用，但最后一个页面引用释放时就会被移除。它不能长期负责比页面活得更久的数据。
- 冷启动先由 `session.sync` 读取消息页，首次 change journal 又在读取水位后刷新快照。同一份 200 条合成消息页被读取两次，每份 453,181 字节；并发的两个 `sync` 已能合并，后续有水位的 catch-up 也不重复拉整页，缺口在首次初始化的职责重叠。

此前决策仍然适用：

- [双向有界消息窗口](../bug-fix/2026-10-09-gui-memory-unbounded.md)：400 条阅读窗口、旧窗口更新侧缺口和分页游标不能被刷新破坏。
- [会话短期变更日志与重连补拉](../feature/2026-10-09-session-change-catchup.md)：必须先读取水位，再应用快照，成功后才能确认水位。

## 决策

缓存账本由 `server-sync` 持有，与 child Store 一起管理生命周期。预取和前台共用访问登记与 payload 清理入口，不再在布局和目录上下文中维护各自的长期缓存账本。

预取 10 会话、前台 40 会话的策略保留；前台访问会提升缓存项，预取不能将其降级或挤出前台缓存。目录键与 child Store 使用相同的归一化规则。淘汰统一清理预取 revision、消息窗口状态、todo、消息、parts 和 delta；前台上下文仍负责自己的分页元数据、乐观消息和 change journal。目录释放同时释放账本，不新增定时器。

冷启动复用 change journal 的初始化协议，将“读取水位 → 加载快照 → 确认水位”作为一次完整工作。普通首载和紧随其后的 checkpoint 共用初始化结果，不再分别读取完整消息页。强制刷新、旧窗口快照、失败重试和旧服务端降级仍遵循原有同步语义。

`createDirSyncContext` 的同步层和 QueryClient 依赖由创建者显式提供；页面消费接口不变，测试可以直接调用实际实现，不需要替换上下文模块。

## 备选与否决理由

- **目录不可见时补一次清缓存**：只修复一个触发点，仍然留下生命周期不同的两套账本，也可能清掉仍有消费者的数据。
- **加载过消息就跳过首次 checkpoint 快照**：消息页与随后捕获的水位之间可能有变更，会把尚未反映的数据当成已同步。
- **继续缩小消息窗口或增加回收计时器**：没有解决缓存所有权与重复读取，反而增加回拉和时序分支。

## 后果

这批优化只处理已由代码和探针确认的缓存积累、重复完整读取，不改滚动、IME、虚拟列表测量或 Electron 行为，也不改变 MCP 进程管理。没有新增模型可见内容、配置项、数据库结构或版本号。

验收分别检查实际保留的数据和实际消息页调用数，不以纯 LRU 单测替代集成验证；内存字节和 GUI 交互体验仍需在实际 GUI 使用中测量，不能从会话计数推断 GB 级收益。
