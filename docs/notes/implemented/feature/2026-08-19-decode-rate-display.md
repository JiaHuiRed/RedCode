# 侧边栏显示解码速率与首字延迟

状态:implemented

## 背景

哥哥看到别的 code agent 显示 `xx tokens/s`，问 RedCode 能不能加。查下来**数据早就在库里**，只是没显示：`message-v2.ts:500` 的 `time.firstChunk` / `time.completed`（埋点见 `processor.ts` 的 `llm.ttft`，分析脚本 `script/ttft.ts`，260811 为排查「首次交互为什么慢」而加）。实测最近 400 条 assistant 消息 **400 条有值、399 条可算速率**，不需要任何新埋点。

## 决策

**两段分开显示，不合成一个「总速度」。**

```
created ──── firstChunk ──── completed
   └ 排队/预填 ┘   └── 吐字/解码 ──┘
```

首字慢和解码慢是**完全不同的两种问题**：前者是排队与预填（供应商侧负载、上下文长度），后者是吐字本身。合成一个数会让它们看起来一样，正好丢掉最有诊断力的那一半。实测样本里这一点很明显——同一个 deepseek-v4-flash，解码在 **15～73 tok/s** 之间摆动四倍，而首字稳定在 2.1～2.8s；如果只报一个总速度，会把「解码忽快忽慢」误读成「整体时快时慢」。

**两个容易搞错的口径：**

1. **分子必须是 `output + reasoning`。** `session.ts:460` 把 `output` 定义成 `outputTokens - reasoningTokens`，只用 `output` 会漏掉思考的字——对 DeepSeek 这类长思考模型会严重低估。
2. **分母必须从 `firstChunk` 起算，不能用 `created`。** 那段是排队/预填，长上下文下能把 60 tok/s 稀释成 20，测出来的就不是解码速度而是排队时间。社区里「同一模型时快时慢」的抱怨，有相当部分可能就是工具拿总耗时算速率造成的。

## 后果

- 侧边栏新增一行 `xx tok/s · 首字 x.xs`，位置在 `in/out` 之前，与既有统计同组。两个值各自缺失时独立隐藏。
- `formatMs` 秒级保留一位小数（侧边栏只有 42 列，`2423ms` 比 `2.4s` 长且没更有用）。
- 测试：`sidebar-context.test.ts` 新增 2 例（秒/毫秒分界、秒级不出现两位小数挤版）。
- 只做了 TUI 侧；GUI 的上下文面板同样有这两个字段可用，未做。
