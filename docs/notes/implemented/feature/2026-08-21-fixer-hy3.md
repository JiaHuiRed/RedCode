# fixer 子代理换用 hy3 关推理档

状态:implemented

## 问题

opencode-go 套餐里有 hy3（腾讯 Hy 推理模型，8x 额度），哥哥想知道它和现在用的模型差多少、能不能顶替部分子进程。当时 fixer 用 `opencode-go/deepseek-v4-flash`（贵），explore 用 `opencode-go/mimo-v2.5`（原生多模态识图）。

## 决策

fixer 改用 `opencode-go/hy3` + `variant: none`（显式关推理）。explore 保持 mimo-v2.5 不动（识图能力不可替代）。seed 与 home 两份 fixer.md 同步改。

bench 实测（`~/.redcode/temp/bench-hy3.mjs`，6 任务 × 2 轮中位）：

| 任务 | hy3 关推理 | mimo-v2.5 | deepseek-v4-flash |
|---|---|---|---|
| 代码输出 | 2.1s | 21.9s | 3.8s |
| 生成 TS 函数 | 4.9s | 69.3s | 8.5s |
| 工具调用 | 2.0s | 6.4s | 2.3s |

- hy3 默认开推理：简单任务也烧 300-5000 推理 token、慢 10-20 倍（code-rewrite 74.6s/4828 推理 tok）；`reasoning_effort: "none"` 后 4.9s/0 推理 tok，判分不掉。
- hy3 单价（models.json）：in 0.0175 / out 0.0725，deepseek-v4-flash 是 0.22/0.66，约 12 倍差距 + 8x 套餐额度。
- 子代理档位机制：`request.ts` 对 `input.small` 走 `smallOptions()`，取 `model.variants` **第一个档位**，不走用户手动选的档位；hy3 的 variants 由 `dataEffortVariants` 按 `reasoning_options` 顺序生成 `{none, low, high}`，第一个恰好是 none。agent frontmatter 的 `variant: none`（`prompt.ts:637` 校验存在才用）是双保险，防止未来 models.dev 数据顺序变化静默改变档位。

## 备选与否决理由

- **hy3 默认档（开推理）**:否决——烧推理 token 且慢 10-20 倍，实测无质量增益。
- **hy3-preview**:否决——网关 `Model is unavailable`，全部 400。
- **mimo-v2.5 换给 fixer**:否决——慢 3-10 倍且 `reasoning_effort` 参数实测无效（隐式推理，档位空转）。
- **deepseek-v4-flash 继续当 fixer**:否决——贵 12 倍，无性能收益。

## 后果

- **hy3 网关侧是纯文本**：实测发图片请求（image_url dataURI / 裸 base64 / OpenAI image 三种格式），模型 reasoning 里明说"用户没有提供图片"——网关剥图不报错。识图任务必须保留 mimo-v2.5（explore）。
- hy3 上下文 256K / 输出 64K，小于 deepseek 的 1M/384K——超大上下文任务别用 fixer。
- mimov2.5 的 low/medium/high 档位在 UI 上可见但请求层不生效（隐式推理），是历史遗留的空转配置，未动。
