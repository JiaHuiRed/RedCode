# 工具输入流独立计账，持续新增调用不能绕过保护

状态：implemented

## 问题

2026-10-22 的 GLM 会话在同一条 assistant 响应中产生 384 个不同调用 ID（383 个 `fff_grep`、1 个 `read`），直到用户中断仍未收尾执行。数据库中的空 input 是 pending 占位，不能证明供应商没有输出参数。

重复失败保护只处理执行失败；普通流静默保护则被持续到来的新事件刷新，两者都覆盖不到这一形态。SDK 按上游不同 ID 创建调用，RedCode 适配器不自行改写 ID；没有原始 SSE，不能进一步归因到模型生成、供应商解析器或代理层。

## 决策

- `experimental.toolInputGuard` 由配置模块校验并显式解析默认值：`maxPendingCalls = 64`、`idleMs = 120000`；支持范围分别为 1–4096 和 1000–1800000 毫秒。
- 仅计尚未收到 `tool-call` 的输入。不同 ID 新增一项，同 ID 重复 start 不重开预算，也不刷新进展时间。
- 仅该调用非空参数 delta 刷新进展；其他调用的新事件、空 delta、重复 start 都不能掩盖它的停滞。持续有参数进展的长输入不按总时长截断。
- 超数量预算时在事件处理路径直接失败；逐调用停滞由 scoped 看门狗失败。两者中断当前响应，均不自动重放。
- `tool-call` 后转入既有本地执行集合，长工具和权限等待继续豁免网关静默计时。
- 进度与终止日志保留 ID、工具名、长度计数和耗时，不记录参数正文；对象显式序列化，避免文件日志只剩 `[object Object]`。

## 备选与否决理由

- **提高重复失败阈值或修改 FFF**：没有实际执行失败，不在故障发生层。
- **新事件统一刷新所有输入**：会原样放过本次持续新增调用的异常。
- **按整段输入生成总时长截断**：会误伤持续输出大量合法参数的调用。
- **超限后自动重试**：可能再次进入同一异常流并重复付费；用户主动继续才发新请求。
- **把参数输入计入本地执行豁免**：参数中断时会获得永久免疫，违背既有[在途工具集合决策](2026-09-16-watchdog-pending-tools.md)。

## 后果与验证边界

默认最多保留 64 个尚未完成的输入，正常需要更多并行输入时可显式调高预算。该上限是可调资源预算，不是模型能力判定；超过配置会明确报错，不会静默遗漏调用。

回归覆盖同步洪泛、单调用停滞被其他 start 掩盖、重复 ID、正常并行和长参数、执行等待及不可重试；测试直接调用生产 guard。供应商真实 SSE 未留存，本次不声称复现供应商产生异常 ID 的内部原因。

## 模型可见四问

1. 提示词、工具定义与正常工具结果不增删、不重排；改变的是异常流的终止边界。
2. 正常请求固定前缀增量为零；配置本身不作为提示词注入。
3. system/tools 前缀不变，不主动使 KV 前缀失效；错误后由用户发起的下一轮按既有历史转换处理。
4. 未新增模型注入项。数量预算由校验后的配置限定；日志不包含参数正文，也不回灌模型。
