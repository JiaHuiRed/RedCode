# 子代理超时收口到请求级看门狗

状态:implemented

## 问题

`tool/task.ts` 曾把 agent 的 `timeout_ms` 套在完整的子代理循环外面：模型请求、推理、工具执行和下一轮请求共用一个倒计时。2026-09-09 的两个 Step Plan 子会话都在精确 300 秒被取消，数据库里已经有连续的 reasoning、tool 和 step-finish 产出，随后才跨到普通 `stepfun`，于是父会话收到的是另一额度池的 quota 错误。

这个判定无法区分“供应商请求没有响应”和“子代理仍在正常推进”。而请求层已经有更窄的看门狗：首事件 75 秒、中途流静默 120 秒；本地工具执行和权限等待不计入网关静默。

## 决策

- 删除子代理总生命周期 `timeout_ms` 与 `fallback_model` 契约。`task` 不再按整个 `runWithModel` 计时、取消或跨供应商重跑。
- 保留请求层看门狗作为唯一的供应商请求 stall 防线：它区分首响应、流事件静默和本地执行。
- 旧配置字段仍可被 JSONC 解析，但在归一化时明确记录 warning 并丢弃，避免旧配置静默改变行为；设置面板与 SDK 不再暴露这两个字段。
- 子代理模型由调用方/agent 定义决定；当前本机的 `explore` 与 `execute` 都固定为 `stepfun-step-plan/step-3.7-flash`，不再有跨额度池兜底。

## 备选与否决理由

- **保留完整子代理生命周期超时**：否决——正常的长推理、工具调用和多轮工作会被误杀。
- **把完整生命周期超时改成子会话活动窗口**：否决——会在 task 层重复实现请求层已有的首事件/流静默/本地执行区分，且无法准确识别底层供应商状态。
- **超时后继续跨供应商重跑**：否决——会把 Step Plan 的请求问题伪装成普通 Step 或其他套餐的额度错误；当前子代理只有 Step Plan 订阅。

## 后果

真实供应商拒绝、网络错误和请求 stall 保留原始错误与请求层重试语义，不再被 task 层统一改写成“子代理总时长超时”。如果将来要增加不同供应商的 fallback，必须在请求错误分类层实现，不能重新把总生命周期计时塞回 `task.ts`。
