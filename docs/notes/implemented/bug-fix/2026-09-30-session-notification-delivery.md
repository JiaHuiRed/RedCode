# 会话提示按实际送达渠道互斥，Windows 快捷方式定向迁移

状态:implemented

## 问题

权限和提问事件先调用 `Platform.notify()`，随后无条件创建应用内 toast；桌面端只在窗口未聚焦时创建系统通知，因此后台同一事件会同时留下两种提示。原接口不返回是否创建通知，调用方无法决定是否需要应用内兜底。

Windows 现场另有两个快捷方式争用 `ai.redcode.desktop.dev`：正确的 `RedCode Dev.lnk` 指向已打包程序，历史 `Electron.lnk` 指向依赖中的 Electron 42.4.1 且没有应用参数。开始菜单把该身份登记为 Electron，点击通知打开 Electron 欢迎页。现有 `.unpackaged` 身份隔离只防止新的开发运行冲突，不迁移历史文件。

## 决策

- `Platform.notify()` 返回 `true` 表示已创建系统通知；跳过或创建失败时返回 `false`，兼容既有返回 `void` 的 mock。权限和提问提示只有在未创建系统通知时才走应用内 toast，保留当前会话及其子会话的抑制规则、设置和声音。
- 异步送达期间保留请求身份；回复、拒绝、切换到目标会话和组件销毁会失效待显示 toast，防止旧结果重新弹出。系统通知创建失败回退应用内提示。未回答时保留 5 秒冷却；回答或拒绝后清除，保证紧接着的新请求仍会提醒，系统通知独占时也遵守这一规则。
- 桌面通知点击依次恢复窗口、聚焦、调用已有会话导航。恢复或聚焦失败不阻止导航，点击处理最终关闭通知；不增加第二套 URL 或协议路由。
- Windows 启动先写入当前 RedCode 身份和可执行文件的快捷方式，写入失败会记录警告且不迁移旧文件。开发快捷方式使用独立身份和绝对应用路径，已有有效启动参数保留。
- 打包运行只迁移精确的 `Electron.lnk`，同时核对其 RedCode AppUserModelID、`electron.exe` 目标和空应用参数；移动到用户数据目录的 `shortcut-backups/`，不覆盖备份、不删除、不扫描或改写其他应用的快捷方式。不改变 userData、数据库或版本号。

## 备选与否决理由

- **直接关闭系统通知**：失去后台提醒，只解决遮挡。
- **删除所有 Electron 快捷方式**：会影响其他应用，也无法回退。
- **再次更换打包版 AppUserModelID**：绕过历史冲突，但引入新的身份和系统设置迁移；现有正确身份不需要变更。
- **用文档提醒用户手动清理**：不能防止其他机器的历史残留复发，迁移应由启动路径承担。

## 后果

`true` 表示通知对象创建成功，不保证操作系统在勿扰模式下展示。应用内兜底保持可用；网页端拒绝通知权限时仍可收到应用内提示。

现场旧快捷方式已备份并核对 SHA-256 一致，开始菜单登记从 Electron 恢复为 RedCode Dev。未重启正在运行的应用；新代码在正常重新构建、启动后生效。

定向回归 34 条通过（app 16、desktop 18），两包类型检查通过，覆盖通知分流、异步取消、回答后的新请求、会话点击和快捷方式迁移边界。Windows 系统通知真实点击仍需在新版正常启动后验证，纯逻辑测试不替代该端到端场景。

模型可见输入、固定提示词、KV cache 和工具 schema 均不改变；没有新增注入项。
