# 记忆快照收窄到跨机共享范围

状态:implemented

## 问题

`seed/scripts/export-memory-backup.mjs` 把整张 `supermemory.db` 导成 `memory/lessons-backup.<host>.md` 并入库推送。这张库是**单库多项目**（`memories.project` 列区分），所以导出会把使用者所有工作区的记忆——包括与本仓毫无关系的私有工作项目——一并写进共享快照。

但快照入库的**目的**（私仓 `.gitignore` 注释自陈，260813 拍板）是「db 不进 git 时，全文的版本化与可回滚」，跨机共享只是顺带；而**共享面本该只有跨项目通用的教训**——就是 `global` 这一档，索引层设计里项目专属的从来不进全局 `MEMORY.md`。整库导出让「备份范围」和「共享范围」混成了一个。

触发路径有两条，都会走到同一个无过滤的导出：`hooks/pre-commit` 在暂存 `MEMORY.md` 时自动导出并 `git add`；项目级记忆不碰 `MEMORY.md`，则由会话手动跑导出再单独提交。

## 决策

`export-memory-backup.mjs` 拆成两份输出：

| 输出 | 内容 | 入库 |
|---|---|---|
| `memory/lessons-backup.<host>.md` | 只含共享项目（默认 `global`） | 是 |
| `memory/local-backup.<host>.md` | 全库，含私有工作项目 | 否（私仓 `.gitignore`） |

共享范围由环境变量 `REDCODE_BACKUP_PROJECTS`（逗号分隔）扩展，默认 `"global"`——不写死。

## 备选与否决理由

- **只加过滤、不做本地全量备份**：否决——260813 入库快照的原始动因就是「只有 db 一份、被写坏无法回滚」，砍掉全量备份等于把这个保护一起丢了。
- **用排除名单（黑名单）**：否决——名单要随新工作区增长，漏登记一个就再漏一次；白名单默认只有 `global`，新项目想共享必须显式登记，失败方向是安全的。
- **改 db 为分库存储（项目记忆落各自工作区）**：暂不动——那是架构改动；本条只解决「不进共享仓」。
- **反向：共享面包含本仓自身的项目（`redcode`）**：暂不纳入——本地验证与文档类事实的跨机价值低，且索引本就在各自工作区、对端没有对应索引；需要时由 `REDCODE_BACKUP_PROJECTS` 显式打开。

## 后果

- 入库快照从「全库」收窄为「共享面」，本机实测 256 条 → 117 条。
- **已写进仓历史的历史条目不会因这次改动消失**——本 note 只解决「以后不再写进去」；存量清理是独立的不可逆操作，须单独决策。
- 另一台机器需要 `pull` 之后重跑一次导出，其快照文件才会同步收窄；在此之前它会继续按旧脚本产出全量文件。
- 全量备份落在 `.gitignore` 内，与 `check-memory-dualwrite.mjs` 无关（后者读 db 与 `MEMORY.md`，不读快照）。
