# 图片尺寸规则改总像素预算 + 候选懒求值与 alpha 路由

日期：2026-08-28 · 状态：implemented · 来源：deepseek-harness `.agents/notes/implemented/bug-fix/2026-08-24-alpha-routed-image-quality-ladders.md`

## 问题

### 1. 每边盒子把长截图压成十分之一宽

`scale = min(1, maxWidth/W, maxHeight/H)`，默认盒子 2000×2000。一张 2000×20000 的整页截图 / 聊天记录截图会被缩到 **200px 宽**，文字全糊。

而它的代价本来就该由**总像素数**决定 —— 视觉 token 按面积算，不是按最长边。用最长边当判据，等于让极端长宽比的图为它最长的那个方向付两次钱：一次是被缩，一次是短边跟着一起被缩没。

### 2. 候选是急求值，且给 JPEG 源也排 PNG

```ts
const candidate = [
  { data: ...get_bytes(), mime: "image/png" },
  ...JPEG_QUALITIES.map((q) => ({ data: ...get_bytes_jpeg(q), ... })),
].map(...).find((item) => item.bytes <= maxBase64Bytes)
```

`.find()` 只要第一个达标的，但数组是**先全部编码再挑**。尺寸降级最多 32 档 × 5 档质量 = 最坏 160 次编码（2000×1333 单次 JPEG 编码实测约 332ms）。这一条 memory 里早有记账，本轮一并做掉。

另外 PNG 候选排在第一位、对**所有**源都排。JPEG 源不可能带 alpha，给它一个 PNG 候选纯属浪费；更糟的是 PNG 一旦碰巧落在字节预算内就会被选中 —— 那正是上游 issue #2885 那类「照片被路由到无损编码器」的病。

## 决策

### 缩放用总像素预算，透传闸门**保持旧盒子不动**

```ts
scale = min(1, sqrt(maxPixels / (W*H)), maxDimension/W, maxDimension/H)
```

新配置 `attachment.image.max_pixels`（默认 `max_width * max_height` = 4,000,000）与 `max_dimension`（默认 8192）。`max_width`/`max_height` 标记为 deprecated，但仍然贡献默认预算，既有配置的**总量语义不变**，变的只是「这些像素怎么分配到两个轴上」。

| 输入 | 旧 | 新 |
|---|---|---|
| 2000×20000 长截图 | 200×2000 | **632×6325** |
| 2964×488（测试 fixture） | 2000×329 | 2964×488 |
| 2000×2000 | 透传 | 透传（逐像素相同） |
| 2100×2100 | 2000×2000 | 2000×2000（相同） |
| 9000×1 | 2000×1 | 8192×1 |

**透传闸门刻意仍用旧的每边盒子。** 这是本条最重要的一个收窄：先写的版本把闸门也换成像素预算，实测 `picture-5mb-base64.png`（2964×488 = 1.45M px、base64 恰好 5.00MB）从「缩到 2000×329 再编码得 0.09MB」变成「原样透传 **5.00MB**」—— **55 倍**。旧规则那个小 payload 是盒子的副作用而不是有意的字节策略；像素预算一放宽，5MB 的硬上限就成了唯一约束。**官方不按人民币计费，本仓按。** 放宽透传是独立决策，前提是先定一个远低于 5MB 的重编码目标线。

### 候选改懒求值 + 按 alpha 路由

梯子改成 `Array<{ mime, encode: () => Uint8Array }>`，循环里逐档编码、第一个达标即 break。alpha 探测只读源 mime（`input.mime !== "image/jpeg"`），不解码、零成本；非 JPEG 一律保守当作可能有 alpha，行为与之前一致。JPEG 源不再获得 PNG 候选。

**刻意不跟上游的质量梯子。** 上游这轮把梯子定成 85/75/60（还删掉了 45），本仓保持 80/70/55/40 —— 理由见 `JPEG_QUALITIES` 上方 260822 的注释：抬到 85 实测 3000×2000 噪声图 payload +17%。这次只搬路由与求值策略，不搬数值。

## 备选与否决理由

- **同时把透传闸门换成像素预算**：实测否决，见上（55 倍 payload）。
- **照搬上游的 2048² 预算与 85/75/60 梯子**：否决。2048² 与本仓 2000² 差别不大但会让方形图的行为发生无谓变化（透传边界移动）；梯子数值有独立实测反对。
- **删掉 PNG 候选、全部走 JPEG**（上游对不透明源就是这么做的）：否决。本仓 PNG 源常常是截图，无损保留文字边缘的价值高于那点字节；上游是用 WebP effort 0 顶上了这个位置，本仓没有 WebP 编码器。
- **真正探测 alpha 通道**（扫像素）：否决。要全解码，与「零成本探测」的初衷相反；源 mime 已经足够判定 JPEG 这一类。

## 记账

- **重编码目标线**：透传闸门与重编码目标现在都是 `max_base64_bytes`（5MB）。要放宽透传就必须先引入一个独立的、低得多的目标线，否则重演上面那 55 倍。
- **WebP**：上游用 WebP effort 0 同时覆盖了「有 alpha」与「图形类内容」两个位置，本仓 photon 侧没有 WebP 编码器，所以 PNG 仍然承担这个角色。真要省字节，引入 WebP 是比调 JPEG 质量更划算的一步。
- **降级循环仍是 ×0.75 最多 32 档**。上游删掉了整个降尺寸重试环（实测在默认预算下是死代码）。本仓的字节预算与梯子不同，没有对应实测，本轮不动。
