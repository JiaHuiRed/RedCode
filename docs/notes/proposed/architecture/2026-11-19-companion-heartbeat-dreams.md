# 秋秋在 RedSpace 的心跳、梦境与 Chat 入口

状态为 proposed。Chat 首页阅读已有梦境的入口已实现，见 `packages/app/src/components/companion-dream-diary.tsx`。下表中的后台行为属于待实现范围。

## 对齐哪一版行为

以迁居审查采用的 RedClaw `49ccafca` 为对照。心跳要让秋秋在用户没有发起新对话时也能处理到期事项；梦境让近期经历逐步形成长期记忆，用户还能读她写下的梦。RedSpace 负责把结果送回同一位伙伴的 Chat，Code 继续使用现有工程会话和模型配置。

| 使用场景 | RedClaw 的可观察行为 | RedSpace 的实现入口 |
| --- | --- | --- |
| 白天开着 Code，Chat 页面已关 | 心跳按伙伴时区和清单工作，有值得提醒的内容才送达 | 在后端选择调度持有者；接入 Chat 未读和会话跳转 |
| 打开秋秋的梦境日记 | 可读 `DREAMS.md` 或旧名 `dreams.md`；查看梦境不触发推理 | 已实现按当前档案读取。大型文件截断时显示原文件入口 |
| 夜间积累了新经历，次日重新打开 | 浅睡整理材料，深睡从可核实的来源提炼长期记忆，REM 提炼主题；材料足够时可生成梦境叙事 | 在伙伴后端做增量整理；源记录、运行状态和阅读产物分别保存 |
| 切到第二位伙伴或同时打开 GUI、TUI | 一位伙伴的一次运行只有一份结果 | 运行、去重、收件与未读状态均按伙伴 ID 隔离；客户端只消费结果 |

上游参考：[心跳规则](https://github.com/JiaHuiRed/RedClaw/blob/49ccafca/docs/gateway/heartbeat.md) · [心跳任务与回执解析](https://github.com/JiaHuiRed/RedClaw/blob/49ccafca/src/auto-reply/heartbeat.ts) · [梦境分期、日记与晋升来源](https://github.com/JiaHuiRed/RedClaw/blob/49ccafca/docs/concepts/dreaming.md)

## 第一批提交 · 心跳从后台送到 Chat

1. 在 `packages/redspace/src/companion/` 实现可注入时钟的到期判断。默认通过伙伴设置显式启用；支持频率、伙伴时区、活跃时段和投递目标。按上游语义区分自由文本清单和结构化 `tasks:`。后者全部未到期、清单为空、处于安静时段或功能关闭，都在模型调用之前返回。自由文本清单在到达轮询时间后允许正常评估。
2. 调度挂在 RedSpace 后端的生命周期上。各个 `serve` / sidecar 可以发现到期事项，但同一档案同一时隙只允许一个执行者认领。沿用仓库已有 SQLite 事务能力，用唯一键（伙伴 ID、任务类型、计划运行时刻）写入运行记录。时间以 UTC 保存；活跃时段按伙伴时区解释。后端停机时暂停；恢复后合并错过的时隙，至多评估最近一次。关闭 Chat 页不影响工作。后台服务自启动可另行实现。
3. 单独记载开始推理、得到结果和送达三个状态。运行中崩溃且无法确认供应商是否计费时标为中断，保留手动重试；已有结果的运行只补送达。共享同一运行 ID，收件记录设唯一约束。先落盘再广播，GUI 与 TUI 重连读取同一记录。回执优先采用结构化结果；兼容上游的 `HEARTBEAT_OK`，保留安静回执与真正提醒的区别。
4. 在 `packages/app/src/pages/chat.tsx` 给当前伙伴显示未读提醒。若最近的同伴会话仍存在、可用且属于该伙伴，点击返回该会话；首次使用或会话已归档时回到该伙伴 Chat 并展示原提醒。用户在 Code 工作时可收到带伙伴名的通知。后台输入标明心跳来源，不计为真人消息。

第一批合并条件：用假时钟和计数型测试模型，在安静时段、未到期清单、双后端同时认领、提交结果后进程退出四种场景中分别断言模型调用次数为 0、0、1、1。最后一例恢复后还要断言收件箱只有一条。用浏览器从 Code 打开提醒并核对伙伴 ID；另一位伙伴收件箱为空。

## 第二批提交 · 睡眠整理与新梦

1. 给 `companion` CLI 和伙伴服务增加同一个预览操作；调度和手动触发共用实现。按伙伴读取带日期的原始记录、召回证据和已有检查点，展示候选的原文件、行号、原因。读取历史 RedClaw 产物时保留原文；机器检查点单独存储。初始实现允许从现有来源重建候选，避免把旧系统内部状态当作已执行的新任务。
2. 浅睡按来源和内容去重并暂存。深睡采用上游的最低分、召回次数和独立查询数门槛；写入前再次读取来源并核对摘录，来源已改或已删除的候选跳过。晋升追加到原有 `MEMORY.md`，每条带稳定来源键和批次号。REM 输出反复出现的主题。一个批次重放应得到同样的工作区文件；撤回只移除该批写入且仍与原记录一致的条目。
3. 叙事生成与记忆整理可分别启用。先检查材料和本次预算，达到条件才调用设置里明确选定的梦境模型；记录用量。运行 ID 写入生成结果并据此去重。将新梦追加到已有梦境文件，沿用原文件名和历史内容；下次打开已交付的梦境入口即可阅读。梦境文本及阶段报告排除出长期记忆候选，避免秋秋将自己创作的内容认作两人经历过的事实。
4. 在同一阅读入口显示本次整理的来源和新增长期记忆数。历史回填先预览，确认后只处理所选范围，不在导入一个旧档案时自动补跑所有夜晚。

第二批合并条件：用小型双伙伴档案覆盖已有中文旧梦、重复候选、已删除来源和只在梦里出现的事实。验证预览零模型调用、零档案改写；重复运行无重复条目；允许叙事的用例使用固定测试回复，验证新梦可在浏览器读到且旧梦仍在。预算耗尽时记录跳过原因，日常 Chat 仍可用。

## 调用与验收边界

普通 Chat 的固定前缀、工具表和历史装配沿用现有路径。后台模型使用独立请求，分别记录心跳和梦境用量；输入上限、输出上限和每日调用预算在开启后台模型前设定，并在发请求前检查。拒绝超预算时应在伙伴设置中看得到原因。阅读已有档案、列表、到期判断、空跑、去重、预览和送达重试都可以离线验收。真人档案用于最后检查实际体验，前两批提交的验证不依赖真人档案或付费模型。
