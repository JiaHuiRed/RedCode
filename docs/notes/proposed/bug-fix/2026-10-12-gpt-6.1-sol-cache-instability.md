# GPT 前缀缓存不稳定：variant 抖动已修，字节级一致仍全灭未消除

### 已排除的假设（附证据，防重复排查）

1. **前缀被客户端改写** —— 否。`request-evidence` 的 `system`/`tools`/`parameters` 三段在模型段内 `change=unchanged`（lAP02Wig 的 sol 段 `parameters` sha 恒为 `8675f2d13dd1`，len 379，仅压缩调用例外），`history` 绝大多数为 `append`（即前序条目 sha256 逐条一致）。
2. **`prompt_cache_key` 漂移** —— 否。同一会话内恒定（lAP02Wig 恒为 `a799e5cd…`，且 luna 与 sol 同值 = 与会话同源）。
3. **账号/端点漂移** —— 否。`accountHash`/`endpointHash` 在单进程内 144 条 transport 记录全部一致。注意 `endpointHash = identity(url)`，`identity()` 用**进程级随机盐**，跨进程不可比。
4. **上下文降级档位**（`contextLevel: soft|prune`）—— 否。同档位既有全灭也有 98.5% 命中（如 `prune` 档 344832/364780 命中）。
5. **并发争用**（后台 GLM 复核子代理）—— 否。14:08:20 那次全灭时并发数为 0。
6. **缓存 TTL** —— 否。14:08:20 全灭距上一请求响应仅 2 秒。
7. **`variant=None` 本身** —— 是症状不是原因，见下。

## 决策

### 根因 ①（客户端，sol 特有，已定位并已修）

**variant/reasoning 参数在 turn 内来回抖动，把请求踢进两个不同的服务端缓存池。**

证据链（会话 cc4mxJ4O，`2026-10-12T010407.log`）：`affinity.reasoning` 哈希在 `6dc38f46a6` ↔ `6e4fe78088` 之间跳变，**每次跳变都紧邻一次缓存丢失**：

| 时刻 | reasoning 哈希 | 结果 |
| --- | --- | --- |
| 01:16:48 | `6dc38f46a6` | 97.0% |
| 01:17:06 | `6e4fe78088` ← 跳变 | **整段全灭（in=146,060）** |
| 01:18:19 | `6dc38f46a6` ← 跳回 | 87.5%（丢失） |
| 01:20:28 | `6e4fe78088` ← 跳变 | 79.1%（丢失） |
| 01:21:05 | `6e4fe78088` | 整段全灭 |

DB 侧同源佐证：该会话 gpt-6.1-sol 的 assistant 消息里 `variant` 为 `high` 27 条、为 `None` 9 条（mode 仍是 `redmind`，非压缩）。`affinity.reasoning` 的两个取值恰好对应 `variant=high` 与 `variant=None`。

`prompt.ts:696-699` 的既有注释已记录同一机制：合成消息（noReply 注入）不传 `model`/`variant` → reasoning effort 从 high 回落 → **"GPT 前缀缓存随参数变化整体作废（实测 146k 输入全 miss，request-evidence parameters sha high→medium 吻合）"**。日志里 01:17:06 那次的 `in` 恰为 **146,060**，与该实测完全吻合。

**为什么只有 sol 特殊**：luna 在同一会话里也换过 variant（xhigh 144 条 / max 69 条），但那是**用户主动切模型**，属预期；sol 的是**合成消息路径静默丢 variant**，在同一 turn 内来回跳。同一进程内 step/glm/luna 都不走这条路径，所以只有 sol 暴露。

已修：`0dc25392` 引入 `sessionVariant` 三级回退（显式传参 > agent 配置 > 会话当前选择，且仅在模型与会话当前一致时继承）。修复前后对比：cc4mxJ4O（修复前）有 9 条 `variant=None`；lAP02Wig（修复后）redmind 模式下 0 条，`affinity.reasoning` 在 sol 段恒定。

### 根因 ②（仍未消除，服务端侧）

**字节级前缀完全一致，仍然整段全灭。**

lAP02Wig 的 sol 段在 14:04:54 / 14:09:04 / 14:13:18 / 14:19:18 共 4 次全灭，同时满足：`system`/`tools`/`parameters` 哈希不变、`history` 为纯 `append`、`prompt_cache_key` 不变、`accountHash`/`endpointHash` 不变、距上一响应 2–157 秒。客户端没有改任何前缀字节，因此只能来自服务端缓存未命中（分区/驱逐）。

对照官方 codex（`E:/AI/codex/codex-rs/core/src/client.rs:284-315`）：官方用 **turn 内复用的 Responses WebSocket 长连接** + `previous_response_id` + `x-codex-turn-state` 三重钉住路由，且明确要求"跨 turn 必须不发"该令牌。RedCode 只有无状态 HTTP + 尽力而为的头部亲和（`session-id`/`thread-id`/`x-redcode-turn`/`x-codex-turn-state`，`0dc25392` 引入），没有连接级钉住，也没有 `previous_response_id` 链。

### 附带发现

`history` 并非严格 append-only。`transition()` 只报首个分歧下标，因此 `change=rewrite` 实际包含"在数组中部插入条目"：lAP02Wig 出现 8 次（`i157: 247→25644`、`i227: 270→10390`、`i744: 363→7306`、`i768: 307→8394`、`i773: 342→10645`、`i855: 341→8670`、`i235: 401→8758`、`i244: 286→7946`）。插入点均距尾部 ≤15 条，对应 reasoning 条目在流式结束后落盘、插到既有消息序列中间，每次吃掉尾部一小段前缀。

## 备选与否决理由

- **归因为供应商/网关问题就此收工**：否决——同进程同端点同账号内 glm/luna/step 均 96.8–97.5%，sol 81.0%；且根因 ① 已定位到本仓 `prompt.ts` 的具体回退链并已修，不是纯外部问题。
- **靠调大重试次数缓解**：否决——全灭是"落到没缓存的实例"，重试不保证改善，且放大全价输入。
- **直接照搬 codex 的 WebSocket 传输**：暂缓——改动面覆盖 llm 传输层，先做低成本的连接复用与可观测性，用数据判断收益再决定。

## 后果

- 根因 ① 已消除，sol 段不再出现 variant 抖动；但根因 ② 使 sol 仍比同环境模型多丢约 10 个百分点，长会话累计全价重读约 2.1M token/会话。
- 待办：
  1. 让 turn 内请求复用同一 HTTP 连接（Bun `fetch` 下显式复用 dispatcher），把亲和从头部尽力而为提升到连接级。
  2. ~~给 `x-codex-turn-state` 加可观测性（是否发出、响应是否带回）~~ **已落地**：`7ff5acb6` 取证补盲 + `c9113c4f` 路由指纹之后，`session/request-evidence.ts` 记录 `turnState`/`turnStateHash`，根因 ② 可进一步定位。
  3. 修 `history` 中部插入：reasoning 条目按序 append，不插队。
  4. 扩展 `request-evidence` 覆盖面：当前只投影 `system`/`tools`/`history`/`parameters`，body 其余字段（`service_tier`/`store`/`include`/`text`）变化只会体现为 `serialized: changed`，无法归因。
- **复发识别签名**：某模型命中率比同环境其他模型低 5 个百分点以上、且 `request-evidence` 的 `system`/`tools`/`parameters` 三段均为 `unchanged` 时，先查 `affinity.reasoning` 哈希是否在会话内出现两个取值。

另有 3 次中段丢失（read 单轮回退 6.1k/7.9k/6.0k，共 ≈20k），history 为 `append` 但下一请求把尾部条目改写（383→8363、291→8260 字符）——即**待办 3（reasoning 条目按序 append）仍未落地**的实测签名：条目在发出后继续长，吃掉尾部一小段前缀。

### 根因①'：压缩链路绕过 sessionVariant 回退（新，客户端）

0dc25392 的 `sessionVariant` 回退只覆盖 `prompt()` 创建的用户消息（`prompt.ts:729-738`）；压缩链路全程绕开它：

1. `SessionCompaction.create`（`compaction.ts:1023`）落压缩父消息时 `model: input.model` **缺 variant**（本例 DB 落盘 `{"providerID","modelID"}` 无 variant 键；上游 `stepSettings.user.model` 为何缺 variant 未定位到行，需在 create 入口加取证日志）；
2. SUM 消息 `variant: userMessage.model.variant`（`compaction.ts:507`）→ undefined；
3. 续跑 followup `{...userMessage}` 展开（`compaction.ts:632`）→ 同样缺 variant；
4. loop 内 assistant 消息 `variant: lastUser.model.variant`（`prompt.ts:516`）→ **连续 25 分钟（08:17–08:41 UTC）所有请求 reasoning 参数走错档**（rsn c60437 ≠ max 的 996e89），等于整个压缩重建落进错误缓存池；
5. 用户 16:41 发真实消息（TUI 带显式 variant=max）→ 参数翻回 → **207,225 token 整段全灭**。

除缓存外还有质量面损失：那 25 分钟会话实际跑在非 max 推理档上。修复方向：在压缩边界（create 的父消息或 SUM/followup 落库处）以会话当前 variant（session 表 model 列）兜底，使父→SUM→followup→续跑全链 variant 恒定；并在 `compaction.create` 入口加一行 `model` 取证日志定位上游丢失点。

**状态（261104）**：已修——`SessionCompaction.create` 以会话当前 variant 兜底（同 prompt.ts sessionVariant 守卫：模型同源且非 "default" 才继承），父消息修好即全链闭环（SUM 507/785、followup 632、continueMsg 895 全部从 parent 继承）；上游丢失点未定位到行，但兜底后不再依赖它，若复发看 DB 里父消息的 model.variant 即可分辨丢在上游还是链内。回归测试：`test/session/compaction.test.ts`「compaction parent inherits session variant when caller model lacks one」+ 跨模型不继承负例。

### 根因② 的今日形态补充

9 次全灭中 6 次是「同形请求 N miss → N+1 miss（前缀纯 ⊃）→ N+1/N+2 恢复 read≈上一请求 in」——服务端缓存写入对后续请求的可见性延迟 1–2 个请求（12s–53s 不等，对照另一会话冷启动后 7s 即命中，非确定性）。`x-codex-routing-hint` 全会话恒定（234/234）、accountHash/endpointHash 恒定、`prompt_cache_key` 恒定。待办 1（turn 内连接级钉住）仍未落地。另：并发双会话不是因素——昨日爆发窗口（16:17–16:44）另一会话 0 条请求。

### 后续待办（261104 排定，当日收口）

1. **连接级钉住（= 原待办 1）——预设被推翻，关闭**：原设想「Bun fetch 显式 dispatcher/keepalive」不成立——bun-types 1.3.13 实证 `BunFetchRequestInit` 扩展选项只有 `tls`/`verbose`/`proxy`/`s3`/`unix`/`decompress`，**无 dispatcher、无连接池控制**（Bun 不读 undici 全局 dispatcher，`util/proxy.ts` 同证）。串行化请求可保单连接但会阻塞并行会话的流式响应，代价不可接受。Node 侧（GUI sidecar）undici `Agent({ connections: 1 })` 物理可行但只覆盖 Node 入口，TUI 主力是 Bun。结论：根因② 的客户端侧无可行动作，缓解依赖服务端写入可见性或换协议。
2. **history 条目按序 append（= 原待办 3）——已归因并落地（261104，见文末修复小节）**：中段回退的真实机制是**并行请求在主轮 assistant 流式中途读库组装 body，把中间态条目带上线**，不是单一「流式结束才落全量」写路径。
3. **修复生效判据（验证项，零成本）**：下次压缩边界后核对 request-evidence 的 `affinity.reasoning` 在全会话单一取值（不再出现 996e89 ↔ c60437 跳变）；DB 里压缩父消息 `model.variant` 应恒等于会话所选 variant。
4. **上游丢失点定位（条件触发）**：仅当「DB 父消息已带 variant 而请求仍错档」时才在 `compaction.create` 入口加取证日志——兜底已使主链不依赖它，不预先加。

## 2026-11-04 修复落地（中段回退）

**归因钉死（日志实证，ses_ffe5e5）**：req cddc629f（16:41:58，agent=redmind）history 尾条目 idx=647 = 383 字符——正在流式中的 assistant 消息投影壳；52s 后该消息收尾成 8363 字符，req 00ca987c（16:42:50）前缀在该条目分叉（change=rewrite）。同形态另有 291→8260（req 6db256b8，08:17:50 压缩边界恢复轮）与 idx=5 的 66→63 微改写（req cddc629f 自身 difference），共 3 次 ≈20k token。机制：并行请求读库组装 body 的时刻落在主轮 assistant「已开始落库、尚未收尾」的窗口内。

**改动**：`session/message-v2.ts` toUIMessages assistant 分支入口加投影守卫——`!msg.info.finish && !msg.info.error`（在途的唯一形态：收尾落 finish、中断落 error）整体跳过不出站；收尾后以完整形态首次出现，投影恢复纯追加语义。

**边界**：带 error 的消息走既有 error 分支（abort 且有实质内容仍保留）；主轮/压缩/续跑组装时序都在收尾后，行为不变；AI SDK 内部 step 请求用内存态，不经此投影。

**测试**：message-v2.test.ts helper 默认补 `finish: "stop"`，新增剥键 helper `unfinishedAssistantInfo`（保住 `"finish" in info === false` 断言）与「在途跳过 / 收尾追加」回归用例；latest 的 3 条 unfinished summary 判定用例改用剥键 helper。llm/compaction/session-replay 测试的 fixture 均显式带 finish 或不走投影，无需改。79 pass、typecheck exit 0。

**活体观察（未归因）**：261104 本修复所在会话自身（GLM 网关，139k/1M）出现整回合 Turn 0%（Miss 263k，回合内多次请求全 miss）——形态与根因② 相似但跨供应商、未取证归因，不作结论。
