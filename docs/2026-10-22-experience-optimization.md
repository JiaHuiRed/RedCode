# RedCode 体验优化建议：启动、流式手感与首页布局

## 目标与基线

- 日期：2026-10-22（Asia/Hong_Kong）。
- 基准提交：`a8049f8afafbf680e9d8aa519e0727c86d8cc298`，包版本 `0.12.17`。
- 状态（2026-10-28 对照）：EXP-01、EXP-02、EXP-03 已实施（分别为 `f2bb3773`、`0939d673`、`61ed9c64`）；EXP-04 尚待测量后决定。EXP-02 的同一录制流前后对比及长代码块体验仍待验证。下文保留 2026-10-22 的基线与建议，不代表当前实现状态。
- 用户目标：打开 TUI/GUI 后更早开始操作，文字输出和会话切换更流畅，首页第一眼更清晰、美观。
- 方法：在 RC21 修复之后重新核对启动、渲染和布局源码，结合已有性能记录筛选切入点。本轮未启动或重启用户程序，未修改产品代码。

此前的 [第三方审计](2026-10-21-third-party-audit.md) 重点是正确性、资源上限与恢复能力。本轮聚焦用户能直接感知的体验，候选收益仍需通过同条件对比确认，不承诺尚未测得的提速比例。

## 推荐顺序

首批建议处理 EXP-01、EXP-02、EXP-03，分别对应启动、日常聊天和首页第一印象。EXP-04 涉及更复杂的布局时序，先测量，再决定实施范围。

| 编号 | 方向 | 用户能感受到的变化 | 已确认依据 | 相对改动量 |
| --- | --- | --- | --- | --- |
| EXP-01 | TUI 启动快路径 | 当前模型与输入框更早可用 | 全量供应商目录仍是启动阻塞请求 | 小至中 |
| EXP-02 | GUI 流式文字节奏 | 快速模型输出更连续，减少成段跳出的感觉 | 内容提交间隔最低 120ms | 小至中，需渲染测量 |
| EXP-03 | GUI 首页视觉层级 | 会话成为主体，主操作更明显，卡片更舒展 | 统计默认展开，宽屏固定占 620px | 中 |
| EXP-04 | GUI 长会话切换 | 减少入场纠偏和位置跳动，改善操作响应 | 强制贴底路径有 90 次纠偏预算 | 较大，收益待 profiling |

这里的改动量是相对判断，不是工时承诺。启动到首个有效画面、启动到可发送消息、切换到位置稳定，应分别计量。

## EXP-01：让 TUI 首次可操作只等待必要数据

### 当前机制

- [sync.tsx:518](../packages/opencode/src/cli/cmd/tui/context/sync.tsx#L518) 启动时立即请求 `provider.list`。
- [sync.tsx:527](../packages/opencode/src/cli/cmd/tui/context/sync.tsx#L527) 把它列为阻塞请求；随后与已连接模型、Agent、配置等结果一起等待和写入状态。
- 全目录保存在 `provider_next`，其业务消费位于 [供应商弹窗](../packages/opencode/src/cli/cmd/tui/component/dialog-provider.tsx#L114)。普通聊天所需的已连接供应商已有单独的 `config.providers` 来源。

因此，全目录的处理、传输及前端接收可能延后必要数据发布，即使用户并不打算打开供应商弹窗。机制已经确认；当前缺少从启动到首次可发送的完整计时，不能据此直接承诺节省多少秒。

### 建议方案

1. 首次可操作只等待已连接模型、必要配置、Agent，以及继续会话所需的数据。
2. 全量供应商目录改为第一次打开“连接供应商”弹窗时请求；也可在首屏可发送后空闲预取。
3. 弹窗使用明确的未加载、加载中、失败和已加载状态，避免把尚未取回的目录当成空目录。
4. 自定义供应商去重等依赖完整目录的操作，应在该目录准备好后再执行。

配置、认证、插件配置 hook 仍是当前可用模型的事实来源，不能为提前显示就绪而用旧数据替代。MCP 已有后台连接机制，日志里连接跨过数秒不等于首屏被它阻塞同样时长，不能把这部分时间当成既定优化收益。

### 验收

- 分别测冷进程、热进程和第二个工作区，从选定工作区到模型就绪且可以发送的时间。
- 单独记录 `provider.list` 的完成时间、响应字节数及客户端处理耗时，识别收益来自哪一段。
- 人为延迟或阻断全目录请求，已连接模型仍能正常进入聊天；供应商弹窗显示对应状态并可重试。
- 对比优化前后相同数据和启动方式的中位数及高分位，不混用开发入口与打包版。

## EXP-02：按当前渲染能力重新校准流式刷新

### 当前机制

[PacedMarkdown](../packages/ui/src/components/message-part.tsx#L170) 的提交间隔为：

```ts
Math.max(120, renderMs * 1.5)
```

最低 120ms 意味着内容提交频率最多约 8.3 次/秒。对于快速、连续到达的模型输出，这个门槛可能让文字表现为一截一截更新。

底层已经实现分块 DOM 更新与稳定前缀增量处理，见 [Markdown 渲染决策及 2026-10-20 更新](notes/implemented/bug-fix/2026-09-07-markdown-block-dom.md)。上层刷新节奏值得在当前实现上重新校准，不能继续用旧版全文解析成本直接推导刷新预算。

[当前 renderMs 的测量](../packages/ui/src/components/message-part.tsx#L197) 是提交到下一次 rAF 的间隔，不等于异步 Markdown 完成解析、清洗与 DOM 更新的真实成本。既有合成预处理基准也不包含完整界面渲染，不能直接当作整帧耗时。

### 建议方案

1. 先记录完整 `parse → sanitize → DOM` 的提交成本、输入响应和长任务，建立现有节奏基线。
2. 低成本文本尝试 33–50ms 的提交间隔，复杂内容仍按实际成本自适应降频。这个范围是实验起点，不是已经验证的最佳常量。
3. 继续直接呈现最新内容，保留稳定前缀、增量块和流式期间的高亮策略。
4. 以最新一次内容为准合并中间更新，确保流结束后最终文本和 Markdown 结构完整。

### 验收

- 用同一份录制的 token 流对比短文本、长列表和大代码块，排除模型服务速度差异。
- 同时观察文字更新是否连续、输入是否跟手、页面是否出现更多长任务。
- 对比最终内容、复制结果及 Markdown 结构，确认没有丢尾段或破坏围栏、列表、引用。
- 短文本提频后，大内容仍能降频让出主线程，不能只优化短回答录屏。

## EXP-03：首页以“继续工作”为视觉中心

### 当前机制

- [HomeUsagePanel](../packages/app/src/pages/home-usage.tsx#L277) 每次挂载默认 `collapsed: false`。
- [USAGE_SURFACE](../packages/app/src/pages/home-usage.tsx#L214) 在宽屏固定占 620px。
- [首页布局](../packages/app/src/pages/home.tsx#L375) 将统计放在会话区前方：宽屏并排、较窄窗口堆在上方。

因此，打开首页时大量空间分配给统计详情，会话标题、卡片和主操作的空间受到挤压。现有组件已经有折叠、骨架及旧数据保留机制，优化重点是默认层级、宽度和操作入口。

以上是源码布局判断，本轮未进行当前窗口的视觉验收。

### 建议方案

| 区域 | 建议呈现 |
| --- | --- |
| 顶部摘要 | 一行紧凑指标：本周花费、输出、活跃会话 |
| 主要内容 | 最近工作、需要处理的会话，以及现有看板/列表切换 |
| 主操作 | 带文字的“新建会话”按钮，层级高于次要图标操作 |
| 完整统计 | 独立展开面板或详情入口，持久保存展开选择 |

视觉上给会话标题和卡片留出更充足的宽度，统一标题、间距和操作层级；保留现有主题特色。展开统计不能重置会话状态，首次加载与返回首页要保持布局稳定。

### 验收

- 对比 1366×768、1440×900、1920×1080 三档窗口的前后截图。
- 每档都能直接找到主要会话和新建入口，主要内容不依赖横向滚动才能操作。
- 比较长标题展示、卡片可读性及摘要与主区的视觉占比。
- 刷新、返回首页和切换项目后，用户展开选择的行为符合约定，加载状态不造成明显跳动。

## EXP-04：根据测量完成信号收敛长会话入场纠偏

### 当前机制与证据边界

- [强制模式预算](../packages/app/src/pages/session/message-timeline.tsx#L1004) 为 90 次。
- [强制模式](../packages/app/src/pages/session/message-timeline.tsx#L1097) 不采用普通模式的沉降提前退出。
- [隔帧调度](../packages/app/src/pages/session/message-timeline.tsx#L1111) 使每次纠偏之间跨过两个 rAF；每次底部锚定涉及高度读取和滚动位置写入。

在 60Hz 条件下，完整预算大致覆盖约 3 秒，但不等于主线程被阻塞 3 秒，也不能把全部入场时间归因于这个循环。现有策略用于应对虚拟列表尚未完成行高实测的问题，直接减少次数可能重新出现落在历史中间的回归。

### 建议方案

1. 先记录实际布局次数、每次纠偏成本、可操作时间和最终位置稳定时间。
2. 评估把纠偏绑定到目标视口行的测量完成、数据版本及尺寸变化，集中合并同一阶段的读写。
3. 保留用户滚动立即让位、IME 保护、消息窗口上限、历史缺口和缓存宽度有效域。
4. 用完成信号和有界兜底共同决定收口，而不是只缩小原预算数字。

### 验收

- 覆盖首次打开长会话、A→B→A 和改变窗口宽度。
- 同时对比强制布局次数、切换到可操作时间及滚动位置稳定性。
- 用户滚动和输入法组合输入期间不能被自动定位打断。
- 保留定位准确性后再判断性能收益；此项属于待测优化候选，不宣称已经定位全部卡顿成因。

## 首批实施与统一验收

建议首批分别交付 EXP-01、EXP-02、EXP-03，保留独立前后对照，避免把启动、渲染、布局一次混改后无法判断收益来源。EXP-04 在取得布局记录后单独决策。

| 场景 | 主指标 | 必须同时观察 |
| --- | --- | --- |
| TUI 冷启动与工作区打开 | 到当前模型和输入框可发送的时间 | 全目录失败时普通聊天仍可用 |
| GUI 相同输出流回放 | 可见内容提交间隔、输入响应、长任务 | 最终文本与 Markdown 结构一致 |
| GUI 首页 | 三档窗口的截图与主要操作可达性 | 展开选择、布局稳定和会话状态保持 |
| 长会话切换 | 可操作时间、位置稳定时间、布局次数 | 滚动意图、IME 与历史窗口语义 |

启动应分别记录首个有效画面和首次可发送；流式应使用相同输入流；视觉应固定窗口尺寸和数据。满足这些条件后，再用录屏、截图及时间分布判断收益，而不是仅凭单次观感或更早显示加载动画。

本文仅归档建议。没有修改产品代码，没有新增性能实测，也不把此前正确性测试通过数当成本轮体验改善的证明。
