## 做得好（值得坚持）

- **split into small commits**：每件事独立 commit，跑 typecheck 后提交，commit message 遵循 conventional commit
- **先确认再动手**：布局修改问清楚方案再改，省的返工（"能跑就别动"原则）
- **用 MCP 查代码**：jcodemunch get_file_outline / get_extraction_candidates / get_repo_health 比 grep 快得多且带签名和摘要
- **问清楚具体意见再改**：布局形态、sidebar 处理、重构范围都先问主人选方案再动手

## 做得不好/教训

- **新 MCP 用得不够主动**：主人提醒"咋不用新的mcp呢"后才频繁用。以后搜索/探索代码第一反应应该是 typegraph / jcodemunch，不上 grep
- **commit message 文件太长**：仓鼠热修的 commit body 写了长解释，message 可以更精炼
- **删除常量后漏修复引用**：removed `USE_NEW_DESIGN` const 后还有一处引用没删，浪费一轮 typecheck
- **截图分析太慢**：分析 4 列花了很多轮对话才搞清结构，应该直接问"截图里分别是什么"
- **提取 UpdateAvailableToast 时留了占位符**：删函数不干净
