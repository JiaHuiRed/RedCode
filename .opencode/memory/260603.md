## 教训

### 1. MCP 使用原则：分场景，不搞一刀切
- **代码搜索/导航（找函数/类/类型/定义/引用）** → 优先 jCodeMunch > codegraph > typegraph
  - 省 grep+Read 两轮调用，节省约 30-40% 工具调用
  - TypeScript 语义导航准确率明显高于 grep 字符串匹配
- **配置文件、JSON、文档** → 直接 Read，不要绕 MCP
- **Git/构建/测试** → Bash 逃不掉
- **纯文本搜索（strings、comments、config values）** → grep 更快
- **MCP 掉线时**（jCodeMunch 经常 "Not connected"）→ 果断切回 grep/read，不要死等
- 核心原则：**哪个快用哪个**，MCP 好用就用 MCP，不好用就用传统工具

### 2. 给哥哥列选项不要把后续版本提前
- 哥哥让我"continue or ask"时，我列了"先做 v0.3.15 / 先做 v0.3.16"作为 v0.3.14 的替代项

- 教训：列选项时严格按 TODO.md 顺序，子项不能跨版本号

### 3. exe 编译后的 MCP 路径解析 — 根因分析
- **现象**：TUI 编译后的 exe 运行时，browsermcp 和 typegraph 启动失败（`-32000: Connection closed`），codegraph 和 jcodemunch 正常
- **根因**：exe 的 `process.cwd()` = `bin/` 目录，`InstanceState.directory` 也是 bin/。相对路径 `./browsermcp-server/index.js` 解析到 `bin/browsermcp-server/`（不存在）
- **为什么 codegraph 正常**：`npx -y` 从 PATH 解析，不依赖 cwd
- **修复过程**（踩了很多坑）：
  1. ~~在 `effect-cmd.ts` 加 `findProjectRoot`~~ → 没用，因为 MCP 读的是 `InstanceState.directory`，不是 `effectCmd` 传入的 `directory`
  2. ~~给 `findProjectRoot` 加多种 exe 路径候选~~ → 还是没用，同样的原因
  3. **最终方案**：在 `mcp/index.ts` 的 `connectLocal` 里直接检测 cwd，向上查找 `redcode.jsonc` 或 `.git` → ✅ 生效
- **教训**：
  - `findProjectRoot` 只影响 `InstanceStore.load({directory})`，但 `InstanceState.directory` 的来源需要追查完整链路
  - 修 bug 要在**问题发生的层面**修，不要在上游修（在 MCP spawn 层修，不在 CLI 入口层修）
  - 每次改完要确认 exe 是否真正包含了新代码（清 dist 再编译，或检查 git log 和编译时间）

### 4. kv 存储默认值迁移
- **现象**：滚动条默认改为 `true` 后，用户看不到滚动条
- **原因**：`kv.signal("scrollbar_visible", true)` 只在 `undefined` 时用默认值，旧的 `false` 仍然生效
- **修复**：在 KV 初始化后加一次性版本迁移（`kv_version`），首次启动时升级旧值
- **教训**：改 kv 默认值时，必须考虑旧用户的缓存值，要做版本迁移
