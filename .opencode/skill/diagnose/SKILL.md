# Diagnose — 形式化诊断循环

遇到 hard bug 走这套流程。**反馈循环是核心**，没有它就别猜原因。

## Phase 1 — 建反馈循环

**这是整个 skill 最重要的一步。** 有一条快速、确定、agent 可复现的 pass/fail 信号，bug 就找到了 90%。没有这个信号，盯代码盯到死也没用。

### 建循环的手段（按顺序试）

1. **失败测试** — 写一个触发 bug 的单元/集成/e2e 测试
2. **curl/HTTP 脚本** — 对运行中的 dev server 发请求
3. **CLI 调用** — 带 fixture 输入，diff stdout 跟已知好人做对比
4. **无头浏览器** — Playwright 驱动 UI，断言 DOM/console/network
5. **回放录制** — 把真实请求/payload/事件日志存盘，隔离重放
6. **临时 harness** — 起最小子系统（一个服务 + mock 依赖），单函数调用触发 bug 路径
7. **属性/fuzz 循环** — bug 是"有时输出不对"就跑 1000 个随机输入找规律
8. **二分 harness** — bug 出现在两个已知状态之间时，自动化"启动状态 X → 检查"供 git bisect run
9. **差分循环** — 同输入跑旧版 vs 新版（或两种配置），diff 输出
10. **人工辅助脚本** — 最后手段。必须人点的话，用脚本引导操作

### 优化循环本身

建好第一版后问自己：

- 能更快吗？（缓存 setup、跳过无关 init、缩小测试范围）
- 信号更准吗？（断言具体症状，不是"没崩溃"）
- 更确定吗？（固定时间、种子、隔离文件系统）

30 秒的 flaky 循环 = 聊胜于无。2 秒的确定循环 = 调试超能力。

### 实在建不了

停下来说清楚。列你都试了什么。问用户要：能复现的环境、录制的 artifact（日志 dump、HAR 文件）、或加临时生产端 instrumentation 的许可。

**没有循环，不进 Phase 2。**

## Phase 2 — 复现

跑循环，确认 bug 出现。确认三个事：

1. 循环复现的失败模式**和用户描述的一致**——复现了错的 bug 就会修错
2. 多次跑都能复现（或非确定性 bug 有足够高的复现率）
3. 已记录确切症状（错误消息、错误输出、慢的耗时），后续验证修复时能对照

## Phase 3 — 提出假设

**先列 3-5 个排序的假设，再测任何一个。** 单假设容易锚定第一个想法就停了。

每个假设必须**可证伪**：说清楚它的预测。

> 格式：如果 ____ 是根因，那么 ____ 会让 bug 消失 / 让 bug 更严重。

列不出预测的假设就是感觉，要么扔掉要么细化。

**把排序列表跟用户过一遍。** 他可能有领域知识瞬间重新排序（"我们刚部署了 #3 的改动"），或者知道哪些假设已经排除过。这一步成本极低、收益极高。

## Phase 4 — 探测

每个探测对应 Phase 3 的一个具体预测。**一次只变一个变量。**

工具优先级：

1. **调试器 / REPL** — 一个断点胜过十条日志
2. **定向日志** — 在区分假设的边界打日志
3. **不要"全量打日志再 grep"**

**每条调试日志加唯一前缀**，如 [DEBUG-db3f]。修完后一次 grep 清干净。

**性能回归**：日志通常没用。先建立基准测量（计时 harness、performance.now()、profiler、查询计划），再二分。先量再修。

## Phase 5 — 修复 + 回归测试

**回归测试写在修之前**——但只在有**正确接缝**的情况下。

正确接缝 = 测试在调用方级别上复现了**真实的 bug 模式**。如果接缝太浅（单调用方测试测不到多调用方触发的 bug），在那写测试只会给假信心。

**如果正确接缝不存在，这本身就是一个发现。** 记下来——代码架构阻止了 bug 被锁定。在 Phase 6 提。

如果存在正确接缝：

1. 把最小化复现变成该接缝上的失败测试
2. 看它失败
3. 应用修复
4. 看它通过
5. 拿原始（未最小化的）场景重跑 Phase 1 反馈循环确认

## Phase 6 — 清理 + 事后复盘

声明已完成之前必须：

- [ ] 原始场景不再复现（重跑 Phase 1 循环）
- [ ] 回归测试通过（或不存正确接缝已记录）
- [ ] 所有 [DEBUG-xxxx] 探针已删（grep 前缀确认）
- [ ] 临时 harness / 原型已删除或移到标记清晰的目录
- [ ] 正确的假设写在 commit / PR message 里——下次来的人能学

**然后问：是什么机制能让这个 bug 不发生？** 如果答案涉及架构改动（无好的测试接缝、调用方纠缠、隐藏耦合），在修复完成后提出来——这时候你掌握的信息比开始时多得多。

## RedCode 专用提示

- **日志第一条**：查 ~/.local/share/redcode/log/ 最新文件，不猜原因
- **符号定位**：优先 jcodemunch（search_symbols、get_blast_radius、get_call_hierarchy），再 grep
- **类型检查**：修复后跑 un run typecheck（对应 package 目录），不跑 	sc
- **连续失败 2 次**：停手，整理已知信息，问用户——不闷头修
